# Standards

Every specification and standard MAIC follows or deliberately borrows from, with the version it follows, where it is used, how closely, and where it departs, so the project does not drift from them. Planned work names the standard it will follow here before it is built.

Status is one of **follows fully**, **follows a subset** (what MAIC uses is as specified; the rest is not used), or **borrows the idea** (MAIC takes the design, not the letter). **Planned** marks a design not built yet.

## First principle: adopt the standard's names; extend, never extinguish

Where a standard defines a concept MAIC has, MAIC uses the standard's names, field names, values and shapes unchanged. What is MAIC's alone is an extension under a namespace that cannot collide, and a client that knows only the standard can ignore every extension and still work.

The example that set the rule (Micaiah, 2026-10-02): OpenAI's API description is the gold standard for LLM communication and processes, and "we can extend, but we shouldn't extinguish". So the engine protocol uses OpenAI's event types (`response.created`, `response.output_text.delta`, `response.completed`), objects, fields (`sequence_number`, `previous_response_id`), parameters and operations unchanged; MAIC's own concepts (the harness's review stream, steering actions, approvals, `judged_by`) are `maic.`-prefixed events and methods and a `maic` object on OpenAI's objects; and where MAIC's code uses another name today, the name changes when the protocol is built: maic-server's `GET /api/sessions/{id}/events?after=N` becomes `starting_after` ([design/engine-protocol.md](design/engine-protocol.md#10-names-openais-extended-under-maic)).

## How to use this list

* **Any change that adds or alters a protocol, a file format or an external API updates this page in the same change**: a new row, a new version, a new deviation, or a deviation removed.
* **Review checks new work against the listed standard**, at the version listed: names first (the principle above), then shapes and behaviour. A departure is either fixed or listed here with its reason.
* **Pins move deliberately.** Where a row names a commit or a tag, bumping it is a change of its own, with this page updated in it.
* Where MAIC's own docs describe a format in detail, the row points there; this page says which standard it is held to.

### Adapter normalizations

What an OpenAI-compatible server (llama.cpp `b11284` so far) sends that the pinned description does not allow is rewritten at MAIC's input boundary, `normalize_openai` in `core/src/openai.cpp`, so everything past the client sees only OpenAI's shapes. Each rule is one line of a table there. None is silent: the call's caller hears each rule and its count (`ChatOptions::normalized`), the agent counts them in its usage report (`maic -p --json` prints them) and writes a `normalized` record `{rule, provider, upstream, count}` to the session, and `maic sessions stats` sums them. An error object also keeps what was replaced and the rules' names in `error.maic.upstream`. `jsonschema_test` checks each rule on fixtures written from llama-server's source: as sent the shape fails the schema, normalized it fits, and each rule alone fixes only its own departure.

| Rule | What llama.cpp sends | What MAIC presents | Why |
| :--- | :--- | :--- | :--- |
| `error_code_string` | `"error": {"code": 500, ...}`, an integer | `"code": "maic_llamacpp_500"`: `maic_`, the provider's `upstream`, `_`, the number; `"maic": {"upstream": {"provider": "llamacpp", "code": 500, "rules": [...]}}` | OpenAI's `Error.code` is a string or null |
| `error_param_null` | an error with no `param` | `"param": null`, the rule named in `maic.upstream.rules` | OpenAI's `Error` requires `param` |
| `logprobs_refusal_null` | `choices[].logprobs` as `{"content": [...]}` | the same with `"refusal": null` | OpenAI requires `refusal` beside `content`; MAIC requests no logprobs today, but the shape is defined and tested |

The code is a value MAIC mints in an open text field, so it carries the `maic_` prefix (the design's rule 4, [design/engine-protocol.md](design/engine-protocol.md#the-convention)). Its middle part is the provider's `upstream`, the software behind it, not its configured name: the shipped `llamacpp` and `llamacpp-2` both set `upstream = "llamacpp"`, so either server's 500 is `maic_llamacpp_500`; a provider without `upstream` uses its name ([settings.md](settings.md#providers)). The original number and that source stay in `error.maic.upstream`. Asking llama.cpp upstream to send these shapes is on the roadmap's Parked list.
