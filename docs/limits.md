# Known limits

What MAIC does not do, or does only partly, in one place. Each entry has a status:

* **accepted**: a deliberate choice; it stays unless the reason changes.
* **expected**: how the thing underneath works; nothing in MAIC can change it.
* **open**: worth fixing; what would fix it is named.
* **addressed**: fixed; kept here for the record, with where.

The feature's own section is linked from each entry. Add an entry when a limit is found, and change its status rather than deleting it.

## Trust and settings Lua

Feature: [harness.md, Directory trust and restricted settings Lua](harness.md#directory-trust-and-restricted-settings-lua-built), [settings.md, Project layers, trust and the chain](settings.md#project-layers-trust-and-the-chain).

* **Custom instruction-file names are not hashed.** *Addressed* (2026-10-01): the names come from `instructions.files` in the global settings, which MAIC reads before it asks about trust, and every one of them, with its `.local.md` variant, is part of the directory's hash ([instructions.md, Trust](instructions.md#trust)).
* **Nested `AGENTS.md` files are not hashed.** *Addressed* (2026-10-01): a project directory's hash covers the instruction files in its subdirectories (and the files they import inside it), and on-demand loading attaches a nested file only when a trusted directory on the chain hashes it, so a new or edited one asks again as the tier says ([instructions.md, Trust](instructions.md#trust)).
* **Nested instruction files past the first 4096 directories are not read.** *Accepted.* The search below a project directory is breadth first in name order, skips hidden directories, `node_modules` and links, and stops after 4096 directories, so it costs little at every start; a file it never reaches is neither hashed nor attached. Would address it: a larger bound, at the cost of start-up time in a very large tree. ([instructions.md, Trust](instructions.md#trust))
* **An import outside the importing directory is not in its hash.** *Open.* An `@path` import that lands in your config directory, or in another trusted directory, is read but hashed by neither, so editing it does not ask again; imports inside the importing directory are hashed with it, and an import of your own files from outside the trusted directories is approved with its SHA-256 ([instructions.md, Imports from your own files](instructions.md#imports-from-your-own-files)). Why: the target belongs to a directory with its own trust (or to you). Would address it: hashing every followed import with the directory whose file imports it. ([instructions.md, Imports](instructions.md#imports))
* **The standard tier counts any uncommitted local edit as yours.** *Accepted.* Under `standard`, an uncommitted change in a git working tree passes, whoever made it on this machine: a build script or a postinstall hook that rewrites `.maic/settings.lua` looks like you. Why: git cannot tell who edited a working tree, and asking about every edit of your own is what `strict` is for. Would address it: `maic trust PATH --level strict` for such a repository, or sandboxed trust so the file's Lua cannot reach the system either way.
* **Server sessions take their settings from the server's startup.** *Open.* A maic-server session gets the settings `maic server start` loaded where it was started; a remote session's workspace contributes its trusted instructions and tools but not its project settings layers. Why: one settings object is shared by every session the server hosts. Would address it: loading settings per session from its workspace, through the same trust check.
* **Restricted Lua had no memory cap.** *Addressed* (2026-10-01): the sandbox level runs a data file in a child process under RLIMIT_AS, RLIMIT_CPU and RLIMIT_NOFILE, and the restricted level refuses early in process (heap checks in the count hook, `string.rep` and `table.concat` checked before allocating); `lua_memory_mb` sets the cap ([harness.md](harness.md#directory-trust-and-restricted-settings-lua-built)).
* **A fully trusted directory runs its settings Lua as you.** *Accepted.* That is what trusting fully means, the same as your own dotfiles; the exploit that started this work runs when trusted fully. Would address it for a given repository: trust it sandboxed (`s` at the prompt, `maic trust PATH --lua sandbox`).
* **Lua tools have no memory cap and keep a few base functions.** *Open.* A user's Lua tool runs in its own state per call with base, string, table, math and bit, no `load`, `require`, `dofile` or `loadfile`, the JIT off and a count hook for Ctrl-C and its 60 s limit, every `maic.*` call authorised by the harness; but nothing caps its heap, and `collectgarbage`, `getfenv`, `setfenv`, `newproxy` and `string.dump` are still there. Why: tools predate the restricted environment. Would address it: building tool states from the restricted environment and its count-hook memory check, keeping the tool's own `maic` table. ([tools.md](tools.md))
* **The restricted level's memory check is not a hard cap.**
 *Expected.* In MAIC's own process the count hook sees the heap only every 1000 instructions, so one allocation between two checks can pass the limit; only the sandbox's child has a kernel limit behind it. Would address it: choose `sandbox`, the default for partly trusted directories.

## The command sandbox

Feature: [harness.md, Layers, rule 6](harness.md#layers).

* **Host sockets reached the sandbox.** *Addressed* (2026-10-01, v0.3.1): the read-only bind of `/` left `$XDG_RUNTIME_DIR` and `/run` in sight and the environment named the session D-Bus, so a sandboxed command could ask systemd to run something outside it. All of `/run`, the runtime directory and the agent socket directories are empty now, and the environment is an allow-list ([releases/v0.3.1.md](releases/v0.3.1.md)).
* **A socket in some other directory is still reachable.** *Open.* The sandbox hides `/tmp`, `/run`, the runtime directory and the directories of the sockets `SSH_AUTH_SOCK`, `GPG_AGENT_INFO` and `NVIM` name; a path socket anywhere else that you can read stays reachable through the read-only bind, for example one in your home directory or under `/var/lib`, or an nvim started with `--listen PATH` that MAIC was not given as `$NVIM`. Why: a read-only bind does not stop `connect()`, and MAIC cannot know every socket on the machine. Would address it: a seccomp filter that refuses `connect()` on `AF_UNIX` sockets (bubblewrap's `--seccomp`), with a way to allow one a tool needs.
* **Live output is dropped when its viewer falls behind.** *Accepted.* A command's output is read at full speed whatever shows it ([tools.md, Live output](tools.md#live-output)); while more than 2 MiB waits for a slow screen or client, newer chunks are dropped and counted, and what still waits 200 ms after the command ends is dropped too, so the end of a fast flood may never show live. Why: the command and its result must never wait for a display. Nothing the model gets is affected, and the result replaces the live view when the call ends. The engine (step 5) adds its own per connection: past 2 MiB queued for one client its tool output becomes skip counts under the same `sequence_number`, so one slow phone never holds up the others; the sandbox's drop still applies when the engine itself cannot keep up.
* **A remote client sees at most 64 KiB of tool output a second per session.** *Accepted.* The engine sends a remote connection the rest as skip counts (`maic.skipped`), so a runaway command cannot crowd approvals and replies off a phone link. The result arrives whole either way, and `maic.item.expand` serves the recorded result afterwards.
* **maic-server's output events name the call, not the item.** *Addressed* (2026-10-02): the engine numbers items (`~<n>`), and every event carries `output_index` where OpenAI's shape has it and `sequence_number` ([engine protocol, as built](design/engine-protocol.md#16-build-order)).
* **The tail of a very long kept output is in memory until the command ends.** *Accepted.* A kept output ([sessions.md, Full output](sessions.md#full-output)) is written as it arrives up to its head (the cap less the tail it keeps, a quarter of the cap and at most 8 MiB); that tail is written when the command ends, so a crash during a runaway command loses that tail, not the head. Why: the tail is the part that changes until the end. Would address it: a ring file for the tail.
* **A redacted kept output loses its timing within a run of one stream.** *Accepted.* `maic sessions redact` redacts each run of one stream's chunks as one text, so a secret split across two reads is still found, and the run becomes one chunk in the copy's index: replaying the copy shows the order of stdout and stderr but not the redraws inside a run. The original keeps its index whole.
* **`cai trans-fairy-write restore` puts back the session file, not its kept outputs.** *Open.* After `maic sessions redact --in-place` the original kept outputs sit beside the backup (`.backups/<id>/<stamp>.d/`); restoring the session leaves the redacted ones in place. Would address it: `restore` moving the `.d` beside a backup back with it.
* **Sandboxed commands in maic-server ignored SIGPIPE.** *Addressed* (2026-10-01): a process that runs an httplib server ignores SIGPIPE, and the disposition was inherited through bubblewrap, so `seq 1 1000000 | head` printed a write error there; the sandbox resets it to the default for every program it starts.
* **The omitted count of a long output was wrong past 128 KiB.** *Addressed* (2026-10-01): the sandbox keeps the head and a rolling tail of a runaway output, and the `[N bytes omitted]` line counted only what was left in that buffer, a number that also varied with how the pipe happened to be read. It counts every byte now; the head and tail the model gets are unchanged.
* **Programs kept under `/run` are missing inside.** *Addressed* (2026-10-01, v0.3.2): `/run/current-system`, `/run/booted-system`, `/run/wrappers`, `/run/opengl-driver` and `/run/opengl-driver-32` are bound back read-only when they exist (sockets inside masked), and the Nix daemon socket at `/nix/var/nix/daemon-socket` is masked ([harness.md](harness.md), rule 6). Setuid wrappers stay inert under `no_new_privs`.

## The engine protocol

Feature: [design/engine-protocol.md](design/engine-protocol.md), steps 1 to 9 and 11 to 14 built (the "As built" notes under its build order).

* **The TUI does not run on the engine yet.** *Addressed* (2026-10-02): the TUI and `maic -p` are in-process clients of an engine; the turn loop, titles, `!cmd` and the session's `:` commands are the engine's ([engine protocol, step 6 as built](design/engine-protocol.md#16-build-order)).
* **The machine's `:` commands still run in the TUI.** *Open.* `:up`, `:down`, `:gpu`, `:trust` and `:untrust` (all but `:trust imports --approve`), `:settings`, `:lazylock`, `:path`, `:open` and `:artifacts` act on the machine rather than a session, so step 6 left them in the TUI; a client on `maic --rpc` cannot send them yet, maic.nvim's interface included (`/up` there answers "unknown command"; `maic up` in a shell or `:MaicTerminal` does it). Would address it: engine commands for them, local only. `:unlock` stays the TUI's either way: the machine lock is reset with sudo at the terminal.
* **A command's question reaches only the client that typed it.** *Open.* The questions a `:` command asks (auto under a dumb harness, a directory's trust on `:cd`, an import from outside, `:init`'s move) come back in its answer (`ask`), not as events, so another client of the session never sees them. Why: they are local only, and one local client was all there was before the daemon. Would address it: an event for them, now that the daemon can have several local clients of one session.
* **A `!cmd` shows to other clients only as its output.** *Open.* No event says that it started, what it runs or how it ended; the exit code goes to the client that ran it. Would address it: opening and closing events for it, now that a second local client can watch through the daemon.
* **maic-server's sessions are not titled.** *Open.* Every session the TUI, `maic --rpc` (maic.nvim) or the daemon opens gets a title from `small_model` after its first turn, however it was opened (`EngineOptions::titles`, step 12); maic-server's are not, as before, and `maic -p` leaves its one-shots untitled on purpose. Would address it: maic-server as an adapter inside the daemon (step 16), its sessions titled with the daemon's.
* **A queued turn's number is provisional.** *Accepted.* `response.create` on a busy lane answers a queued response with the turn number it will run as; when one queued before it is cancelled, it moves up a number. Why: turns are numbered in the order they run, as the checker holds them. ([design, section 11](design/engine-protocol.md#11-steering))
* **Ending a paused turn shows as an empty response.** *Accepted.* `keep`, `halt` or `cancelResponse` on a paused turn open a successor and end it at once, so the turn closes on a terminal event with `maic.final: true` as every turn does. Why: the protocol has no event that closes a turn without a response, and adding one would leave OpenAI-only clients without the end.
* **A steer cannot reach back into the history.** *Accepted.* A `drop` on a paused turn, or while a tool runs, trims nothing (the reply already went into the history with its calls), and a `halt` on a paused turn tells the model that its work was discarded rather than removing the partial reply already kept. A steer accepted as the reply ended applies to what follows it, the reply staying whole in the history. Why: the history is append-only.
* **A ban's steer found at the very end of a reply is a plain cut.** *Accepted.* The filter holds back the last few characters (and a pattern's window) until the reply ends; a steer entry that matches only in that tail is cut as a plain ban is at that point, not steered. Why: the call is already over, so there is nothing to stop.
* **Per-agent steering waits for agent sessions.** *Addressed* (2026-10-02, step 14): a background task's session runs as its agent, and `agents.NAME.steering` narrows what can be sent to it by its own id (and `:steering` there shows it). A foreground task still runs inside its parent's call, steered as the parent's running tool.
* **Steering does not cancel a review.** *Open.* A steer withdraws a waiting approval or question and cancels a running tool; the smart harness's review in flight is not an event yet, so it is stopped by the cancel without `maic.review.cancelled`. Would address it: step 10 (review events).
* **A live item keeps its provisional id.** *Open.* An item written during a turn is `~<n>` on the stream; its `response.output_item.done` does not give the `<file id>#<line>` it became, so expanding it or paging from it waits for the next `attach` or page, which names it by its file id. Why: the agent writes its record after the event goes out. Would address it: the record's line handed back to the engine before the done event.
* **An item finished as a client attaches can be missing until the next page.** *Accepted.* `attach` reads the transcript and subscribes in one step, but the agent writes a record just after its event: an item whose event went out before the snapshot and whose record was not yet written is in neither. Why: one lock for the transcript and the stream would hold every turn up on the disk. The next `attach` or `listConversationItems` has it.
* **History has no pictures.** *Open.* A turn's images are not kept in the transcript, so a history item never carries them and `maic.item.expand` has no image parts. Would address it: keeping attached images beside the session, as full output is.
* **maic-server and the TUI read history their own way.** *Open.* maic-server's `GET /api/sessions/{id}` still folds `entries` from the transcript, and the TUI's `-c` and `-r` draw from `load_session`, where a `clear` hides what came before it; the protocol's history shows every displayable record. Would address it: step 16 for maic-server; the TUI's scrollback on `attach`'s items once it can show what `clear` hid without changing what you see now.
* **An output item does not say who judged it or that it was denied.** *Open.* `maic.judged_by` and `maic.status` are not set: the review is not an event yet and the agent's callbacks do not say a call was refused. Would address it: step 10 (harness paths and review events); a checker panel's verdicts and `judged_by` then go on the stream too ([The checker panel](#the-checker-panel)).
* **A subagent's work shows on its parent's stream as notices.** *Addressed* for background tasks (2026-10-02, step 14): a task with `background: true` has its own session and stream, its first event names its parent, and its approvals show on the parent's stream naming its session. *Accepted* for a foreground task: it keeps step 6's notices (`maic.notice` with `kind` `tool_call` and `tool_result`) and its approvals name the agent only. Why: a foreground task is a tool call of the parent's turn, steered and cancelled with it; giving it a session of its own changes nothing it can do.
* **maic-server keeps no index file.** *Open.* The daemon keeps `<state>/engine/index.json` (step 13); maic-server's engine keeps none, so its sessions end with the server. Would address it: maic-server inside the daemon (step 16).
* **Background sessions live in the process that holds them.** *Addressed* (2026-10-02, step 13) while the daemon runs: `maic daemon start`, and the TUI and maic.nvim open their sessions in it, so `:q` leaves a working session working and the next interface reaches it ([daemon.md](daemon.md)). Without the daemon, or with a flag only this process can honour, a session still lives in its interface's own engine as before: `:q` says so when one is still working and quitting parks them.
* **Two engines can load the same transcript.** *Open*, narrowed (step 13). While the daemon runs, every interface without a process-only flag is its client, so one engine holds each session. Still possible: two interfaces without the daemon, or one that runs its own engine (`--system`, `--context`, `daemon = "off"`, ...) resuming a session the daemon holds; both append to it. Would address it: a lock beside each loaded transcript that a second engine respects, or refusing such resumes while the daemon answers.
* **The `airtight` tier is refused.** *Open.* There is no conformance stamp yet, so an engine whose default (`protocol_tier`) is `airtight` will not start, and a session whose directory is enrolled `airtight` is refused (`maic_tier_unavailable`). Would address it: step 18 (the stamp written by `release.sh`, recorded streams).
* **An agent's protocol tier is read but not applied.** *Addressed* (2026-10-02, step 14): a background task's session takes its agent's `protocol_tier` (never below its directory's floor), else its parent's tier; a task's session resumed later keeps its recorded tier. Sessions that are no task still run as no agent.
* **An idle parent does not react to a task's report.** *Accepted.* A report that arrives while the parent's turn runs reaches the model at the next step; one that arrives while the parent is idle goes into its conversation as context and the model reads it with the next message, and the person sees `maic.task.completed` at once. Why: starting a turn nobody asked for would let a task's output act unprompted, in auto mode without a person. Would address it: a setting that starts a turn on a task's end, if wanted.
* **A report that arrives after the parent's last model call waits for the next turn.** *Accepted.* A note posted while the parent's final model call runs is not delivered into that turn: no automatic successor is started for it, so it becomes context for the next turn. Why: the same as above, and a successor would need a user turn to carry it.
* **A background task's spend reaches its parent's budget when it ends.** *Open.* Its tokens are added to the session's when its first turn ends; while it runs the parent's `budget_tokens` does not see them, though the task's own budget is capped at what was left when it started. Would address it: sharing the running count between the two agents.
* **A task reports once.** *Accepted.* Only a task's first turn is its job: a message typed into its session after that, by switching into it, runs as in any session and is not reported to the parent. `task_result` knows the tasks of the parent's current load; one from before a park reported as a note.
* **`maic -p` does not wait for background tasks.** *Accepted.* The one-shot ends when its turn ends; a task still running is interrupted and parked with the engine. Why: `maic -p` prints one turn; a job that must finish belongs in the foreground there.
* **`:tier` lasts for the load.** *Accepted.* A session is fixed at the tier its start record names (raised to its directory's floor when that is stricter); a `:tier` change is announced and holds until the session is parked, and a resumed session starts at its recorded tier again. Why: the start record is the session's own statement of how it ran, and a change mid-session is the exception. Would address it: a record for the change, if a case needs it to survive a resume.
* **Daemon sessions have no nvim host.** *Expected* (open question 8). A session in the daemon is no nvim's descendant, so a write is not `:drop`ped into nvim, there is no diff in nvim for an approval and no `diagnostics` tool, even when the TUI attached to it runs inside nvim. Would address it: an attached nvim answering host requests over the protocol (`host.diagnostics`).
* **`!cmd` in a daemon session runs in the daemon's environment.** *Accepted.* Its PATH, virtualenv and variables are those the daemon started with, not the terminal's that typed it; likewise a relative `@FILE` for `:system` or `:prefill` is read from the daemon's directory (`$HOME`; `:image`, `:luafile`, `:export` and `:cd` resolve against the session's workspace). Why: the daemon runs the session. Would address it: the client passing its environment with the command, judged as the command is, and `@FILE` resolved against the workspace.
* **Trust given with `--trust` is this process's.** *Expected.* A directory trusted for one run only is not trusted in the daemon, so such a run stays in its own engine and says so.
* **Some `response.create` fields are accepted and not applied.** *Open.* `instructions`, `tool_choice`, `max_tool_calls`, `truncation` and `include` are read past, and a response's `tools` is `[]`. Would address it: each when a client sends it.
* **The engine checks every event it sends.** *Accepted.* At `guarded` each event is validated against its schema and the ordering machines before it goes out, a cost on the path of a command's output; `open` turns it off. When the engine cannot keep up, the sandbox drops output chunks for display as it does for any slow viewer; nothing the model gets is affected.
* **A flood of output pushes older events out of the ring.** *Accepted.* The ring keeps 10,000 events or 8 MiB, so a client that drops during a large output may have to attach again (`maic_resync`). Why: the ring only bridges a dropped connection; history comes from the transcript (step 11).
* **`protocol.log` has no size cap.** *Open.* The guarded tier appends a line per fault; a misbehaving client could grow it. Would address it: rotating it as the audit trail rotates its files.
* **The checker does not yet tie activity to turns, nor check reviews.** *Open.* `ordering.json` holds the session, response, item, content part, action, approval, question and steer machines and the turn and steer rules; `activity` against the turn and the review machine join with step 10. The Python `jsonschema` cross-check of recorded streams (design section 15) is not run.

## Sessions and the workspace

* **`:cd` does not reload Lua or script tools.** *Accepted.* `:cd` moves the harness root, shell commands, the project settings layers and the instruction files; the user's Lua and script tools stay those loaded at start. A `:reload` is planned. ([cli/README.md, Commands](../cli/README.md#commands))
* **`maic sessions rehome` leaves subagent sessions behind unless asked.** *Accepted* (by design). Only the named sessions move; `--subagent` moves their `sub` sessions too, `--subagent-only` only those. A subagent's transcript still finds its parent by id. ([sessions.md, Homes](sessions.md#homes))
* **`:init` moving a session takes only the `sub` sessions in its own home.** *Accepted* (by design). When `:init` (or a relocate) moves the running session into the project's home, its subagent sessions that a default `maic sessions rehome` left in another home stay there; `maic sessions` and `maic sessions state` still find them by the parent's id. `maic sessions rehome ID --subagent` moves them when wanted. ([sessions.md, Homes](sessions.md#homes))
* **The `:init` ask path is not in the TUI suite.**
 *Open.* The question `:init` asks when a session worked outside the project ("move it into the project's home anyway?") is covered by the core tests (`init_move_check`) but not driven through the TUI. Would address it: a `tests/test_tui.py` case that reads and writes outside a project, runs `:init` and answers. ([sessions.md, Homes](sessions.md#homes))

## The audit trail

Feature: [audit-trail.md](audit-trail.md), [leak-audit.md](leak-audit.md).

* **An unrecorded session left nothing to audit.** *Addressed* (2026-10-02): with the audit trail on, every tool call of every session, recorded or not, leaves one entry (the call and the harness's decisions, never text or output) that `maic-leak-audit` reads until the entry retires ([audit-trail.md](audit-trail.md)). Off by default.
* **The trail is not tamper-evident.** *Open.* Entries are 0600 files of yours; anything running as you can edit or delete them. Would address it: chaining each entry's hash to the one before, or signing them with a key the agent cannot reach.
* **Write calls carry their text into the trail.** *Accepted.* The entry keeps a call's arguments as given, so `write_file` and the like keep what was written until the entry retires. Why: the judge needs the call as made. Would address it for a given setup: a shorter `stale_days` with `archive = "off"`, or `maic audit-trail purge`.
* **Off-site moves are never automatic.** *Accepted* (by design). `maic audit-trail offsite` prints the commands and runs none; the archive grows until you act. Why: copying audit data off the machine is your decision each time.


* **Side threads and a running turn take turns on a single-slot local server.** *Expected.* A llama-server with one slot serves one request at a time, so a side thread asked while a main turn runs waits for it. Would address it: a second slot (`--parallel`) where the card has room, or the side server. ([roadmap.md](roadmap.md), [llamacpp.md](llamacpp.md))
* **whisper-server's ready pattern is read from stderr.** *Expected.* whisper-server says it is ready only in its log, so `maic up whisper` waits for `compute buffer (decode)` in its stderr; a whisper.cpp release that changes that line makes the start wait out its timeout. Would address it: a health endpoint in whisper-server, then polling it like the llama servers. ([diction.md, Setup](diction.md#setup))

## nvim

* **llama.vim maps normal-mode `<Tab>` and `<Esc>` globally while enabled.** *Expected.* Not only while an instruction runs; a normal-mode `<Esc>` of your own and llama.vim's replace each other in load order. MAIC's spec turns them off. ([models.md, Code completion](models.md#code-completion))
* **The nvim interface has none of the TUI's own commands.** *Accepted.* `/cmd` in the input goes to the engine; what the TUI does itself (`:set`, `:theme`, `:e`, `:stash`, `:copy`, `:h`, Lua mode, `:q`) has nvim's own counterpart there (its options, colorscheme, `:e`, registers, `:h maic`, `:lua`, `:q`). ([nvim.md](nvim.md#nvim-as-maics-interface))
* **The nvim input highlighter sees only nvim's bundled parsers.** *Accepted.* `highlight = "nvim"` starts `nvim --embed --headless -u NONE`, so treesitter parsers your config installs are not there; fenced code in other languages is left plain. Would address it: starting it with your config, at the cost of your plugins' start-up time on the first keystroke. ([settings.md](settings.md))
* **`bare = true` in a settings file connects to the host nvim, then drops it.** *Accepted.* The host connection comes before the settings are read (so the settings Lua can use `maic.nvim`), so `bare = true` there takes effect only after; `--bare` and `MAIC_BARE=1` never connect. ([nvim.md, Bare](nvim.md#bare))
* **The lazy-lock hash file writes the path relative to `$HOME`.** *Expected.* `sha256sum` cannot expand `~`, so the line is `<hex>  .config/nvim/lazy-lock.json` and is checked from your home directory (`cd ~ && sha256sum -c ...`). ([lazy-lock.md, Files](lazy-lock.md#files))
* **`maic nvim setup llama-vim` refuses when any config file merely mentions llama.vim.** *Addressed* (2026-10-01): only lazy.nvim's resolved spec (its plugins and disabled lists, queried from the headless nvim) refuses, when it has llama.vim from somewhere other than MAIC's own file; a file that only mentions it is a warning (`init.lua mentions llama.vim; it is not loaded as a plugin, continuing`). ([nvim.md, maic nvim setup llama-vim](nvim.md#maic-nvim-setup-llama-vim))

## The checker panel

Feature: [harness.md, Checkers](harness.md#checkers-a-panel-of-judges-built).

* **A metered judge is reached without asking first.** *Open.* The rule that a paid or limited-free model reached for automatically is asked about first ([roadmap.md](roadmap.md), background task follow-ups) is not built yet. On escalation `dual-9b` and `dual-4b` send the call to Claude Haiku 4.5 on your Claude plan with no prompt; choosing the setup in your global settings is the only consent, and only your global file can choose it. `escalate` keeps it to the calls the local judge does not allow, and `primary` with Qwen alone never reaches it. Would address it: that rule, applied to a metered judge.
* **The panel's verdicts are not on the engine protocol.** *Open.* Each judge's verdict and `judged_by` are in the transcript, the audit trail and a `checked:` notice, which reaches every client as `maic.notice`; there is no `maic.review.*` event and the output item's `maic.judged_by` is not set. Would address it: step 10's review events ([The engine protocol](#the-engine-protocol)).
* **A local judge on another model than the session's swaps models.** *Expected.* llama-server keeps one model resident (`--models-max 1`): a judge on the main server with another model evicts the session's model on every check, and one on the side server needs room on the card beside it (a 4B judge beside the 9B at 16k does not fit 8 GB). Why: one 8 GB card. Would address it: nothing in MAIC; choose the setup whose first judge is the session's model (`dual-9b` with `qwen-9b`, `dual-4b` with `qwen-4b`). `llamacpp/current` counts as the file it links (MAIC resolves it at start), so a linked 9B text model matches `qwen-9b`.
* **A cancelled check waits for the judge to notice.** *Expected.* A judge past its `timeout` is cancelled the way Ctrl-C cancels a turn: a local request is closed within about 100 ms, a Claude Code request at its next check, and its process may be replaced on the next escalation, which costs a start. Would address it: nothing needed unless timeouts become common; then a longer `timeout` for that judge.

## Model providers

Feature: [settings.md, Claude Code as a provider](settings.md#claude-code-as-a-provider).

* **A `cli` process carries its earlier requests.** *Accepted.* One Claude Code process per provider, model and purpose serves up to `max_requests` (20) requests, and the CLI keeps each in its conversation: later reviews see earlier ones, the tokens it reports (and the reviewer's spend against `reviewer_budget_tokens`) grow with that context, and in maic-server one process serves every session. Why: starting the CLI costs seconds per request, which every reviewed action would wait for. Would address it: `max_requests = 1` (a fresh process per request), or a process per session for the helpers too, as the agent already has.
* **Claude Code's built-in plugins still load, and auto-memory leaves a directory.** *Expected.* By default (`--setting-sources ""`) the CLI skips your user, project and local settings: your enabled plugins, hooks from settings and your `~/.claude/CLAUDE.md` (measured against Claude Code 2.1.285: the login still works and the cached input drops by about 1.3k tokens). Its built-in plugins (`cc-plugin-agents-md`, `cc-plugin-telemetry`, `cc-plugin-diff`) load either way, and Claude Code's auto-memory creates an empty `~/.claude/projects/<encoded directory>/memory/` entry for the directory it runs in; MAIC keeps that directory fixed per provider (`<state>/cli/<provider>/`), so only one entry ever appears. Why: only `--bare` skips the built-in plugins, and it refuses the claude.ai login (API key only), so it cannot run on your plan. Would address it: a Claude Code flag that skips built-in plugins and auto-memory while keeping OAuth.
* **A CLI error's status is inferred from its text.** *Open.* A failed `result` line carries no HTTP status, so `API Error: NNN` in its text gives one, and limit wording ("limit", "usage-credits", "quota") counts as 429 for `is_usage_limit`; anything else has status 0 and is not retried. A Claude Code release that words its limits differently would be read as a plain error. Would address it: a structured status field in the CLI's result line.
* **A Claude Code preset runs a subagent only when asked for or under a Claude model.** *Accepted* (Micaiah's rule, 2026-10-02). It spends her Claude plan's usage, so the automatic pick (a preset's `subagent`, the rule, a subagent's `on_limit`) never takes one under a parent on another model; the agent's `model` pin or the `task` call's `model` still can. "A Claude model" is read from the model's id or its provider's kind (`anthropic`, `cli`), so a Claude model served under a name without "claude" through another kind is not recognised. ([settings.md](settings.md#model-presets-and-tiers))
* **Requests for one purpose take turns.** *Accepted.* Two reviews on the same CLI model at once wait for each other, since they share one process. Would address it: a small pool per purpose, if parallel subagents make it matter.
* **A conversation Claude Code has not followed is handed over as text.** *Accepted.* As the agent, one process carries a conversation. When the history stops matching what that process has had (compaction, undo, a ban's cut, a resume, a changed mode prompt or tool list, a process stopped past `max_agents`), a new process gets the whole conversation as one labelled user turn: earlier calls and their results written out as text, its thinking not carried. Why: Claude Code keeps its own conversation, and stream-json has no way to load one. Would address it: a CLI option to start from a given history.
* **Claude Code itself runs outside MAIC's sandbox.** *Accepted.* Its own tools are off, so it acts only through MAIC's tools, which MAIC's harness judges and its sandbox confines as always; the `claude` process itself runs with your login and its network access to Anthropic, as for the helpers. Why: it needs `~/.claude` and the network, which the sandbox removes. Would address it: running it under bubblewrap with only those let through; Micaiah trusts its basic behaviour enough not to, and the general wrapper is parked in the [roadmap](roadmap.md#parked).
* **A message sent mid-turn rides on a tool result.** *Accepted.* While Claude Code waits on MAIC's calls, a message you send (or a note from the harness) reaches it appended to the last call's result, labelled `[User]`, so it arrives at its next step as it would for MAIC's own model. Why: Claude Code reads a new user message only between turns.
* **Claude Code caps a tool result's size too.** *Accepted.* Over `MAX_MCP_OUTPUT_TOKENS` Claude Code cuts an MCP result before its model sees it, on top of MAIC's own caps; the full output stays in MAIC ([sessions.md, Full output](sessions.md#full-output)). Would address it: setting `MAX_MCP_OUTPUT_TOKENS` in its environment, if MAIC's caps are kept below it.
* **Summaries move from a remote `compact_model` only for remote sessions.** *Accepted* (by design). A local session's summaries stay on its own model even with `compact_model = "claude-sonnet-cli"`, as titles do with `small_model`; the reviewer has no such rule and follows `small_model` wherever it points.
