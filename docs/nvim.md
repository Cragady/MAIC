# MAID inside nvim: maid.nvim

Two halves that meet over nvim's own socket. The nvim side is a plugin in this repository, `maid.nvim/`, which is MAID's interface inside nvim (the conversation and the input as nvim buffers, the engine as its job; [below](#nvim-as-maids-interface)) or runs MAID's own TUI in a terminal, and sends buffers, selections, diagnostics and the quickfix list into its input. The MAID side finds the nvim it runs inside and connects back as a msgpack-rpc client, so the host becomes MAID's editor: files open there, approved edits show as diffs there, the theme follows its colorscheme, and the user's Lua can reach `vim.*`. The model gets almost none of that, on purpose (below).

## The nvim side: the plugin

Standard layout: `plugin/maid.lua` (the commands, nothing else loads until one is used), `lua/maid/init.lua`, `doc/maid.txt` (`:h maid`), tests in `tests/`. Install and every option: [maid.nvim/README.md](../maid.nvim/README.md).

| Command | Does |
| :--- | :--- |
| `:Maid [args]` | Opens MAID (`open = "split" \| "vsplit" \| "float" \| "tab"`), or focuses the one this tab already has: nvim as its interface (`ui = "nvim"`, the default), or its TUI in a terminal (`ui = "terminal"`, and for arguments only the TUI takes: `-p`, `-i`, `-c`, `-r`, `--context`, `--image`, `--fork-at`, `--bare`, a prompt). `args` are added to `maid` when it starts. |
| `:MaidTerminal [args]` | MAID's own TUI in a terminal, whatever `ui` says. |
| `:MaidSteer ACTION [NOTE]` | The interface's running or paused turn: `steer`, `drop`, `further`, `interrupt` (pause), `keep`, `halt`. |
| `:MaidNew [--bg\|--park\|--stop] [DIR]` | Another session in this tab's engine, in focus, in a conversation buffer of its own (`/cd DIR` follows with a DIR). The session left becomes what `leave.switch` in MAID's settings says (by default a working one goes to the background and an idle one is parked; `"ask"` asks with `vim.ui.select`), unless a flag says otherwise ([settings.md](settings.md#leaving-a-session)). |
| `:MaidSwitch [--bg\|--park\|--stop] [ID\|TITLE]` | Goes to another session (a parked one, or any transcript by id, is resumed); alone, the switcher (`vim.ui.select`): a new session first, then this session's background tasks (`↳`), then every other with its own tasks under it, each with what it is doing, its model and its workspace. |
| `:MaidFork [--bg\|--park\|--stop]` | Forks this session into a second one and goes to it. |
| `:MaidBg` | Sends this session to the background (it keeps working, its buffer still written) and opens the switcher. |
| `:MaidPark [ID]`, `:MaidStop [ID]` | Ends this session (through the switcher, to pick where to go) or another: park for now, stop for good (it stays a transcript); a working one is asked about first. |
| `:MaidToggle` | Hides this tab's MAID window (MAID keeps running) or shows it again. |
| `:[range]MaidSend` | With a range, those lines as a fenced snippet headed with the path and line numbers; without one, the buffer's path for the agent to read. Visual mode gives the range. |
| `:MaidDiagnostics[!]` | The buffer's LSP diagnostics (`!`: every buffer's), one `path:line:col: severity: message` line each. |
| `:MaidQuickfix` | The quickfix list, the same shape. |
| `:MaidInterrupt` | Stops MAID's running turn as its first Ctrl-C does, from any window: in the interface `cancelResponse` to the engine, else `rpcnotify(chan, "maid_interrupt")` when MAID is connected, else Ctrl-C typed into this tab's MAID terminal. |

Text goes into MAID's input as a paste and is never sent by itself: in the interface, into the input buffer. Otherwise the plugin finds MAID through `nvim_list_chans()`: the client named `maid` whose `pid` attribute is this tab's terminal job (with no MAID terminal in the tab, the newest `maid` client), and calls `rpcnotify(chan, "maid_send", text)`; `require("maid").command(":theme mono")` sends `maid_command`, run in MAID as if typed. When MAID is not connected (it was refused, or it is an older build), `:MaidSend` writes the text into the terminal job as a bracketed paste (`ESC [200~ ... ESC [201~`), which MAID also takes into the input whole, in any mode.

Every option and its default is one table, `require("maid").defaults` (`:h maid-defaults`): the layout, the keymaps and whatever comes next. `require("maid").setup(opts)` (lazy.nvim's `opts`) deep-merges `opts` over it with `vim.tbl_deep_extend("force", ...)` and sets the keymaps, `<leader>m` then `m` (open), `t` (toggle), `s` (send the path; in visual mode the selection), `b` (the whole buffer), `d` / `D` (diagnostics, every buffer's), `q` (quickfix), `c` (interrupt). In MAID's own buffers `<C-c>` interrupts too, buffer-local (`buffer_keymaps`; passed through to MAID in terminal mode); `<C-c>` is never mapped globally. The interface's buffers also get `pause` (`<C-s>`), `resume` (`<C-q>`), `send` (`<CR>`) and `send_insert` (`<M-CR>`). `keymaps = false` sets none; a table moves or drops single ones by name. It never overwrites a mapping: before each default key it checks `maparg()` and `mapcheck()` for that mode, skips a key another mapping holds or shares a prefix with, and reports every skipped key once per session in one `vim.notify` warning naming the key, the mode and what holds it (the description, or the script and line from the map's `sid`). A key the user names in `keymaps` is set anyway, and reported if it shadows something.

In MAID's terminal, `<Esc>` goes to MAID (its input is vim-like and needs Esc for normal mode) even when the user has a global `tnoremap <Esc> <C-\><C-n>`: maid.nvim maps `<Esc>` to itself buffer-local, noremap and nowait, in that terminal only (`terminal_passthrough`, a set of keys), so the global mapping keeps working everywhere else. `terminal_escape` (default `<C-\><C-n>`, nvim's own, which needs no mapping) leaves terminal mode there. MAID's terminal gets the filetype `maid` before its job starts, so a `TermOpen` autocmd can skip it (`filetypes` in the defaults table).

`:checkhealth maid` (`lua/maid/health.lua`, the check itself in `lua/maid/keymaps.lua`) lists every key maid.nvim sets, every key llama.vim uses when it is installed (`g:llama_config` set, or `autoload/llama.vim` on the runtimepath; its defaults and older option names are mirrored from `autoload/llama.vim`), and the keys MAID's own input needs in its terminal (Esc, Ctrl-W, Ctrl-P, Shift-Tab, Ctrl-Z, Ctrl-C, Alt-Enter), against the user's mappings in the modes each is used in, global and buffer-local: it opens a plain file buffer, a scratch buffer of filetype `maid-input` and a terminal of filetype `maid` in a tab of its own, reads what the user's autocmds mapped there, and closes them. Each key is an OK, WARN or ERROR line with a fix hint per collision: ERROR for a key MAID needs that never reaches it in its terminal (the hint is `terminal_passthrough`), WARN for a skipped or shadowed key, two keys sharing a prefix, or an insert-mode key that starts with a printable key (so typing it waits `timeoutlen`). Keys are compared as `keytrans()` names, so `<C-w>` typed as `\x17` and kept with a modifier match.

### nvim as MAID's interface

`:Maid` with `ui = "nvim"` (the default), and `maid --ui nvim` from the shell, make nvim MAID's whole interface (`lua/maid/ui.lua`). The engine runs as `maid --rpc` (with `cmd`, `args` and `:Maid`'s arguments), the tab's job, and the plugin speaks the engine protocol to it over the job's stdin and stdout, JSON-RPC one message per line ([design/engine-protocol.md](design/engine-protocol.md)): `maid.hello` as `maid.nvim` with the capabilities `tool_output` and `autocmds` and `collapse_over = 0`, then `createConversation` (or `maid.session.resume` for `-c` and `-r` through `maid --ui nvim`) and `maid.session.attach`. One interface per tab, like the terminal.

* **The conversation** is a scratch buffer of filetype `maid` (markdown with treesitter, falling back to the markdown syntax), written only by the plugin: `❯` your messages, the replies as they stream, `⏺` each tool call with its output indented under it (green or red once it ends; a `!cmd` the same), `↯` each steering action, notices, and the footer `▣ model · time · tool calls` per turn. An output of `fold_output` lines or more (default 4) and the model's reasoning are folded closed once done, as manual folds, made again whenever a window shows the buffer; `za` and your own fold keys open them. The winbar shows the title, model, mode and what the session is doing (`PAUSED: <C-q> resumes`). A window whose cursor is on the last line follows the stream. Highlight groups `MaidUser`, `MaidTool`, `MaidToolOk`, `MaidToolErr`, `MaidNotice`, `MaidError`, `MaidSteer`, `MaidFooter`, `MaidThinking` link to standard groups by default.
* **The input** is a scratch buffer of filetype `maid-input` under it (`input_height` rows), an ordinary buffer for every motion, mapping and plugin you have. `<CR>` in normal mode and `<M-CR>` in insert mode send it (`buffer_keymaps.send`, `.send_insert`) and empty it. `/cmd` runs an engine `:` command (`maid.session.command`; `//` sends a message starting with one slash), `!cmd` a shell command (`maid.session.shell`); while a turn runs, a message goes to it at its next step (`response.steer`), else it starts the next turn (`response.create`).
* **Floats.** An approval opens a float over the bottom of the conversation, focused when you are in that tab: `y` yes, `n` or `<Esc>` no, `N` no with a reason, `a` always, `t` trip the harness, `e` opens the file in your editing window, `d` (for a write) the file against the proposed content (`maid.approval.proposed`) as a diff in a new tab, `<C-c>` no and cancel the turn. A question shows its options (a digit picks one, `<CR>` types an answer, `<Esc>` gives none); an engine command that asks (`ask` in its result) takes one of its keys. They come one at a time, in order, and close when answered anywhere (another client, the engine withdrawing them); `:Maid` focuses a waiting one.
* **History.** `attach` gives the last three exchanges and what is still in progress (the reply so far, a running command's last 8 KiB), drawn as the live events draw them. While earlier history is left, the first line says so; moving the cursor there (`CursorMoved`), or `:MaidOlder`, asks `listConversationItems` for the ten exchanges before the oldest shown and draws them above it, the view staying where it was.
* **Steering.** `<C-c>` (`buffer_keymaps.interrupt`, also `:MaidInterrupt` and `<leader>mc` from any window) cancels the turn, or stops a running `!cmd`. `<C-s>` (`pause`) pauses it (`maid.steer` `interrupt`) and opens the pause menu: `<C-q>` resumes, `s` steer, `d` drop, `f` further, `k` keep, `h` halt, what is in the input going with `s`, `d` and `f` as their note; `<Esc>` closes the menu to type a message, which resumes the turn when sent. `<C-q>` (`resume`) resumes from either buffer. `<C-s>` and `<C-q>` work in insert mode in the input too.
* **Keys** are buffer-local in the two buffers and follow the never-overwrite rule: a key your FileType autocmd already holds there is left alone and reported. `:checkhealth maid` and `maid nvim keymaps` check them in a scratch conversation and input buffer.
* **User autocmds** (`MaidTurnStart`, `MaidToolCall`, `MaidApproval`, `MaidFileWritten`, `MaidTurnEnd`, the table below) fire from the plugin as it renders the events, with the same `data`; `maid.file.written` also runs `:checktime`. The engine, nvim's child, still finds `$NVIM` as its host for the `diagnostics` tool and `maid.nvim` in your settings Lua.
* **Sessions.** A tab's engine holds every session opened in it, each a view with a conversation buffer of its own under the tab's one input (`:ls` shows them as `maid://conversation/...`); events go to their session's buffer, so a background session keeps writing its own. Its approvals and questions wait until you switch to it, with one notification naming it; the winbar counts the other sessions, how many wait for you and how many finished. A parked or stopped session's buffer goes once no window shows it. `:h maid-sessions`.
* **The end.** Closing nvim leaves the session in each tab's focus as `leave.quit` says, as quitting the TUI does (a case set to `"ask"` asks with `vim.ui.select` first, and the answer is sent before nvim goes), then closes the engine's stdin. When the engine exits on its own, the conversation says so with the last of its stderr.

`maid --ui nvim` (or `ui = "nvim"` in MAID's settings) execs `nvim -c ...` with your config, puts this MAID's `maid.nvim` first on `'runtimepath'` after the config has run (lazy.nvim resets the path at its setup), calls `setup()` if your config did not, and opens the interface in the first window with this binary as `cmd` and the agent's flags as `args` (the descriptor goes through `MAID_UI`, which the plugin removes from nvim's environment before starting anything). It is refused with `--bare`, inside nvim (`:Maid` is the interface there) and beside `-p` or `--rpc`; with `--context`, `--image`, `-i` or `--fork-at` `--ui nvim` is an error and `ui = "nvim"` stays in MAID's own interface for that run, saying why. Trust is settled at the terminal before nvim starts. When nvim is installed and `ui` is not chosen, MAID says once at start that `--ui nvim` exists (`<state>/ui-offered`). The installed tree carries the plugin as `share/maid/maid.nvim`.

### `maid nvim keymaps`

The same check from the shell, against the user's own config: `nvim --headless -i NONE -n -V1<log>` with stdin, stdout and stderr on `/dev/null`, `--cmd 'let g:maid_keymap_check = 1'` (maid.nvim's `setup()` then plans its keys and sets none, so the user's own mappings are what is checked), and `-c` loading `maid.nvim/lua/maid/keymaps.lua` from MAID's tree by path (so it works whether or not the config installs maid.nvim; when it does, the user's configured copy and options are used). It dispatches `User VeryLazy` first so lazy.nvim's lazy-loaded plugins map their keys, writes the report as JSON and quits; `-V1` makes nvim record the file and line of mappings made from Lua. It runs in its own process group with `$NVIM` dropped from its environment and is killed at 60 s. It prints the collisions with their fixes (`--all`: every key; `-u FILE`: that config instead of the user's init) and exits 0 with none, 1 with collisions, 2 when nvim could not run. `maid doctor` prints a one-line summary.

Every run from the user's config is kept in `<state>/nvim/keymaps.json`: the collision ids (a key, a mode and what holds it, without line numbers), their sha256 hash, and the hash of `lazy-lock.json` at the time. When the lazy-lock watch sees a `lazy-lock.json` that differs from the one the record was made at (at start, and at each turn end), MAID runs the check once in the background and reports any collision the record did not have as a notice, `a plugin update added keymaps that collide: maid nvim keymaps`, with each one listed; on a machine with no record yet it says how many it found. A machine without a lock file or without nvim stays quiet, and `--bare` never runs it.

### `maid nvim setup llama-vim`

`maid nvim setup llama-vim [--dry-run] [--remove] [--yes]` adds [llama.vim](models.md#code-completion) to a lazy.nvim setup as one file MAID owns. It looks first and changes nothing while it looks:

1. **lazy.nvim.** nvim has to be on PATH and lazy.nvim installed at `stdpath("data")/lazy/lazy.nvim` (`$XDG_DATA_HOME`, `$NVIM_APPNAME`). Without that directory your init is not run at all, since a bootstrap snippet in it would clone lazy.nvim. With it, a headless nvim with your config (stdin, stdout and stderr on `/dev/null`, `$NVIM` dropped, `GIT_ALLOW_PROTOCOL=file` so nothing can be cloned, killed at 60 s) answers whether `require("lazy")` loads and whether your config called its setup (`require("lazy.core.config").spec` is set). Any of these missing: it says which, prints the spec to paste once you have lazy.nvim, writes nothing and exits 0. No other plugin manager is touched.
2. **The import.** The same nvim lists the modules your spec imports (`{ import = "plugins" }` entries in `require("lazy.core.config").options.spec`, or `setup("plugins")`); the first one that is a directory of your config, `<config>/lua/plugins/`, is where the file goes. With none, it does not edit your init files: it prints the import to add, the file to save the spec as, and exits 0.
3. **The file.** `<import dir>/maid-llama-vim.lua`, the spec from [models.md](models.md#code-completion) after a header: MAID as its writer, the date, `maid nvim setup llama-vim --remove` to undo it, and the docs section. A file of that name without MAID's header is refused (exit 1). Only lazy.nvim's resolved spec decides whether llama.vim is there already: when `require("lazy.core.config").plugins` (or its disabled list) has llama.vim from anywhere but MAID's own file, it refuses and names where it comes from (the files its functions were defined in; when lazy.nvim cannot trace it, the `.lua` and `.vim` files of your config that name llama.vim), exit 1, printing MAID's settings to merge by hand. A file that merely mentions llama.vim (a comment in `init.lua`, a note) is a warning, `init.lua mentions llama.vim; it is not loaded as a plugin, continuing`, and the setup goes on. MAID's own file is updated in place with a diff, or left alone when it already holds the spec.

It shows the plan (the file, its content or the diff, the import it relies on) and asks yes or no; off a terminal it needs `--yes` (exit 2 without), and `--dry-run` shows the plan and writes nothing. Afterwards it says what is next: open nvim (lazy.nvim installs llama.vim on its next start, or `:Lazy sync`); that changes `lazy-lock.json`, which `maid lazy-lock` reports until you run `maid lazy-lock record`, and MAID re-runs its keymap check after that lock change; and, only when missing, `maid models install qwen2.5-coder-7b --link` (no coder linked) and `maid up llamacpp-fim` (the completion server is not running). `--remove` deletes only that file, and refuses one without MAID's header, with the same question. `-u FILE` runs nvim with that init instead of yours (the tests use it).

It is a user command: as a tool call it is denied in every mode, over any allow list, and the read-only classifier counts it as a write (the sandbox's read-only home would stop the write anyway).

## The MAID side: finding the host

nvim sets `$NVIM` to its server socket for every job it starts, so a MAID in an nvim terminal knows where its host listens. MAID connects to it only when all of this holds, checked before any request is sent:

1. `$NVIM` is a path (an address like `127.0.0.1:6666` is refused) to a Unix socket owned by the user running MAID.
2. After connecting, the listening process's credentials (`SO_PEERCRED`) say it runs as the same user.
3. That process is one of MAID's ancestors: its pid is found walking MAID's parent chain through `/proc/<pid>/stat`. nvim 0.10 and later run the server as a child of the TUI process, and the terminal job as a child of the server, so the server is always in the chain.
4. When the socket has nvim's default name, `nvim.<pid>.<n>`, the pid in the name is the process behind it.

Anything else is refused, and the reason is the first line in the conversation (`nvim: not connecting to $NVIM (...)`); MAID then runs as it would outside nvim. A socket of another user, of an unrelated nvim, or of a process that merely sits in `$NVIM` gets nothing.

**For tests only:** `MAID_NVIM_TRUST_SOCKET=1` skips the ancestry part (3), so a test can connect MAID to a headless `nvim --listen` it started itself. It is ignored unless `MAID_TESTING=1` is set as well; the ownership checks still apply. Nothing outside the test suite should set either.

Connected, MAID calls `nvim_set_client_info("maid", ..., "remote", {}, {pid = ...})` so the plugin can find it, the status strip shows `nvim`, and `:nvim` says what the connection gives. The connection happens before the settings files are read, so their Lua can use `maid.nvim` too. When the host goes away a notice says so and everything falls back.

## Bare

`maid --bare` (also `MAID_BARE=1`, or `bare = true` in settings) starts MAID with nothing from nvim: no `$NVIM` host connection even inside nvim's terminal (maid.nvim then uses its fallbacks: a bracketed paste for `:MaidSend`, Ctrl-C into the terminal for `:MaidInterrupt`), the built-in input highlighter even with `highlight = "nvim"` (`:set highlight nvim` is refused), no theme following nvim's colorscheme, `:theme nvim:NAME` refused with a message naming bare, no lazy-lock notice and no `lock≠`, no keymap check after a lazy-lock change. MAID's own settings, themes (including saved `nvim-NAME.lua` theme files, which are MAID's files), Lua and script tools still load, and `:e FILE` still runs `$VISUAL` / `$EDITOR` when asked. The status strip shows `bare`; `:nvim` says what is off. `--bare` and `MAID_BARE=1` never connect; `bare = true` in a settings file is known only after the files are read, and the host connection comes before that (so the settings Lua can use `maid.nvim`), so it is dropped right after. `--ui nvim` ([nvim as MAID's interface](#nvim-as-maids-interface)) is refused together with `--bare`.

## What the connection gives

* **Inbound.** `maid_send` text is appended to the input (after a blank line when there is a draft), never sent; `maid_command` runs as if typed; `maid_interrupt` does what the first Ctrl-C does to a running turn, a running `!` command or a pending approval or question (stops it, answers no), and when MAID is idle shows `nvim: nothing to interrupt (MAID is idle)` instead of clearing the draft or arming the quit. Notifications are handled on the connection's own thread and handed to the UI, never acted on from the reader.
* **`:e FILE`** (relative to the workspace) opens the file in the host with `:drop`, in the window you edit in: the current window unless it is a terminal or a float (MAID's own), else the previous window, else any plain window in the tab, else a new split. Outside a host `:e FILE` runs `$VISUAL` / `$EDITOR` / `nvim` on it in MAID's place. `:e` alone still edits the input.
* **At an approval prompt**, `e` opens the file being asked about the same way, and `d` (for `write_file`, `edit_file`, `multi_edit`, `apply_patch`) opens a new host tab with the file against a scratch buffer holding the proposed content, both `diffthis`, the scratch buffer read-only and wiped when closed. Answer in MAID's window as usual.
* **User autocmds** fire in the host through `nvim_exec_autocmds("User", {pattern = ..., data = ...})`, as notifications (MAID never waits on them). Every `data` has `session` (the session id).

  | Pattern | When | `data` |
  | :--- | :--- | :--- |
  | `MaidTurnStart` | a turn starts | `session`, `model` |
  | `MaidToolCall` | the model calls a tool | `session`, `tool`, `path` (absolute, `""` for none), `summary` |
  | `MaidApproval` | MAID asks, then again with the answer | `session`, `tool`, `path`, `summary`, `reason`, `verdict` (`"pending"`, then `"yes"`, `"no"`, `"always"`, `"trip"`) |
  | `MaidFileWritten` | a tool changed a file (write, edit, patch, a move's two ends, a delete, a Lua tool's `maid.write`) | `session`, `tool`, `path` |
  | `MaidTurnEnd` | the turn is over | `session`, `model`, `tool_calls`, `seconds`, `interrupted` |

* **`:checktime`** runs in the host after every file a tool changed and after `:undo`, so an open buffer reloads (or asks, if it has unsaved changes).
* **The theme follows the host** (`follow_nvim_theme`, default `true`). On connect, MAID registers a `ColorScheme` autocmd in the host (`nvim_create_autocmd`, in its own augroup) that `rpcnotify`s MAID's channel; on connect and on every notification, MAID reads the highlight groups with `nvim_get_hl(0, {name = ..., link = false})`, maps them with `theme_from_nvim` (the same table as `:theme nvim:NAME`, [settings.md](settings.md#from-neovim-colorschemes)) and applies them with `apply_theme` as a session-only theme named `nvim:<colors_name>`: nothing is written to the themes directory, and `style` entries in settings still win. `follow_nvim_theme = false` keeps `theme`; `:theme NAME` stops following for the session and `:nvim theme` resumes. No headless nvim is started for this; the host answers.

## Lua

The user's own Lua in an interactive session (the settings files as the session reads them, `:lua`, `:luafile`) gets a `maid.nvim` table while a host is connected, and none without one (nor in `maid -p` or `maid lua`, which never connect):

| Function | Runs in the host |
| :--- | :--- |
| `maid.nvim.exec(code, ...)` | `nvim_exec_lua(code, {...})`; returns what the chunk returns (`maid.nvim.exec("return vim.fn.getcwd()")`) |
| `maid.nvim.buffers()` | the listed file buffers: `{bufnr, path, modified, loaded}` |
| `maid.nvim.diagnostics(path)` | `vim.diagnostic.get()` for the buffer showing `path` (relative to the workspace), or every buffer without one: `{path, line, col, severity, message, source}`, 1-based |
| `maid.nvim.current()` | the editing window (not MAID's terminal): `{path, cursor = {line, col}, selection = {from, to, text}}`, the selection being the last visual one in that buffer, by lines |

A failed call (an error in the host, no answer within 5 s, the host gone) is a Lua error saying so.

## The harness rules

Everything the agent does through the host is an action like any other ([harness.md](harness.md), layer 25):

* The model has one tool from the host, `diagnostics {path?}`, offered only while a host is connected. It is a Read action on the file, or on the workspace when `path` is left out (then only files inside the workspace are reported), judged exactly like `read_file`: a key or credential is never read, a path outside the workspace is asked about in manual and plan modes, every decision is in the transcript.
* Lua tools (the sandboxed ones the model calls) get `maid.nvim.diagnostics(path?)` and `maid.nvim.buffers()`, each authorised through the same step as `maid.read` as a read of the file or the workspace, answering only for files in the workspace. They do not get `exec` or `current`.
* Nothing lets the model run Lua in the host or change a host buffer. A model's edit is a file write through the harness with its preview, undo point and approval; the host sees the file change and reloads it on `:checktime`.
* The host's requests to MAID are notifications only; a request (`rpcrequest`) is answered with an error, so nvim never blocks on MAID.
* `maid nvim setup` is never run for the model: `run_shell` refuses it in every mode, whatever an allow list says.
