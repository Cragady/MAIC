# Roadmap

This is the driver: work is picked from the top of the "Next" list, and nothing lands that is not on it or a quick fix. The rules in [harness.md](harness.md) and [cleanroom.md](cleanroom.md) apply to all of it. What is built is listed at the end, so the list above it stays honest.

Status of the built parts in detail: [README.md](../README.md), [cli/README.md](../cli/README.md).

## Next, in order

### 1. nvim as MAIC's interface

When nvim is installed, MAIC can run its core as an engine and use nvim as the whole interface: the conversation in a buffer (nvim folds for tool output, nvim's own diff for edits, treesitter markdown), the input as a real nvim buffer (every motion, mapping and plugin the user already has, instead of MAIC's reimplementation of vim), approvals and questions as floats, the theme simply the user's colorscheme. `maic --ui nvim` (and `ui = "nvim"` in settings; offered once at first run when nvim is found) starts nvim with maic.nvim and the engine as its job. The engine speaks one protocol, JSON-RPC over stdio (`maic --rpc`), carrying the same messages as maic-server's API, so this interface and the web app (the unified remote interface item) share it. The FTXUI interface stays for machines without nvim and as the fallback. The two-way relationship this completes: MAIC uses nvim outside of nvim (as its interface, highlighter, colorscheme source and package store), and nvim uses MAIC outside of MAIC (maic.nvim). When nvim is the interface, MAIC's own key handling steps aside and the user's nvim mappings rule (Micaiah's example: whatever `<leader>y` does in her nvim, it does in MAIC's buffers), and MAIC adds only what it needs, under maic.nvim's never-overwrite rule. `:Maic` defaults to this interface once it exists; the terminal mode (MAIC's own TUI in an nvim terminal, today's maic.nvim) stays as a fallback. `--ui nvim` is refused together with `--bare` (`:h bare`), which takes nothing from nvim. The same interrupt keys (`:MaicInterrupt`, `<leader>mc`, `<C-c>` in MAIC's buffers) send an RPC cancel to the engine. MAIC's buffers get the filetypes `maic` (the conversation) and `maic-input` (the input), so plugins can include or exclude them (a completion source, a statusline, an autopairs plugin that should stay out). Depends on maic.nvim; shares the protocol work with the unified remote interface.

### 2. Other agentic tools

Other agent CLIs as parts of MAIC, at three levels, each on the user's own login and plan, never MAIC's.

* **L1, text only.** An external agent CLI as a text-only model backend: `claude -p` with `--output-format stream-json` and its own tools turned off, used where MAIC needs text and no actions: the diction scribe, the smart harness's reviewer, session titles and compaction summaries. A provider kind like any other, chosen per role.
* **L2, MAIC's tools.** An external agent runs the loop with its built-in tools disabled and MAIC's tools served to it over MCP, so MAIC's harness judges every action (modes, approvals, the tripwire, the transcript) exactly as for its own model. Usable as a `task` subagent or as the main agent; its output is treated as data, like any model output.
* **L3, its own tools.** An external agent using its own tools, only as an explicit opt-in per agent definition, and confined to the sandbox.

Claude Code first (the only one installed here), opencode next.
* **One harness per action, never two** (Micaiah's concern, 2026-10-01). The plain Anthropic Messages API has no server-side harness for tool actions: the model only proposes a tool call and MAIC executes it, so with an API model MAIC's harness is the only judge of what runs (Anthropic's content safeguards apply to what the model says, not to MAIC's actions). Claude Code is different: it has its own permission rules and, in auto mode, its own action classifier. So for each level: L1 (text only) runs no actions, nothing to judge. L2 (Claude Code driving MAIC's tools over MCP) makes MAIC's harness the single authority: Claude Code's built-in tools are off and MAIC's MCP tools are pre-allowed in Claude Code, so it neither prompts for nor classifies them, while MAIC's harness judges every call. L3 (an external agent using its own tools, explicit opt-in) does the opposite: that agent's own harness governs its own tools, MAIC labels the session with whose harness is in charge, confines it to the sandbox, and records what it reports, without judging the same actions a second time: when the external agent runs with a smart harness of its own (Claude Code in auto mode, with its action classifier), MAIC's local harness for that session is dumb by default (no local reviewer call, so no doubled review and no doubled cost) and the dumb-plus-auto warning does not apply, since a model is already reviewing on the other side. MAIC's fixed rules still hold underneath as the floor (forbidden terms, trip patterns, trust, the sandbox, self-protection), because those are rules, not a second judgement. If the external agent runs without a smart harness of its own (a bypass mode), MAIC keeps its local smart harness, or warns as for dumb plus auto. Anthropic's server-side tools (web search, code execution) run on Anthropic's machines outside MAIC's harness and stay off unless a setting enables them, with a notice.

Level 1 built (2026-10-01): the provider kind `cli` and the shipped `claude-cli` provider run `claude -p` headless with stream-json in and out, as a text-only model for `small_model`, `reviewer_model` and the new `compact_model`; presets `claude-haiku-cli` and `claude-sonnet-cli` on the user's own login and plan; one persistent process per provider, model and purpose (reused, replaced after `max_requests`, respawned when dead, reaped on exit, stderr to `<state>/logs/claude-cli.log`, a timeout per request); usage limits from the CLI's result lines become `ApiError`s, so the reviewer's and summaries' fallbacks work; tool schemas are refused. Verified (fake-`claude` tests in `llm_test` and `agent_test`): the CLI is started with every built-in tool off (`--tools ""`), no MCP server (`--strict-mcp-config` and an empty `--mcp-config`), `--permission-mode dontAsk` and no settings files (`--setting-sources ""`, which a live check against Claude Code 2.1.285 showed keeps the plan login), so it takes no actions and MAIC's harness stays the only judge of what runs. Level 3 remains, and diction's scribe still runs its own `claude` process ([settings.md](settings.md#claude-code-as-a-provider)).

Level 2 built (2026-10-02): with tool schemas, the `cli` provider runs Claude Code as the agent (the session's model or a subagent's) on MAIC's tools over MCP. MAIC serves them from a unix socket in the runtime directory (mode 0600), which Claude Code reaches through `maic mcp-bridge SOCKET` named as its only MCP server and pre-approved with `--allowedTools mcp__maic`; its built-in tools stay off. Each batch of calls it makes ends the model's reply as tool calls, MAIC's harness judges and runs them as for any model (modes, approvals, the reviewer, the tripwire, the transcript), and the next request answers them over MCP; a message sent mid-turn rides on the last result. One process carries each conversation (at most `max_agents`); one it has not followed is handed to a new process as one labelled turn. Verified with a fake `claude` that speaks MCP (`llm_test`, `agent_test`, and `cli_smoke` through the real binary and its bridge); the real `claude` was not run. MCP is pinned in [standards.md](standards.md) at revision 2025-11-25.

### 3. Side conversations (`:btw` and `:aside`)

`:btw QUESTION` opens a side thread forked from the main conversation at that point (a fork pointer, sharing the history without copying it), in a side pane in MAIC's interface and a split or float in maic.nvim. It answers, and the user keeps chatting in that thread afterwards; the main conversation is untouched, and a running main turn keeps running. `:aside QUESTION` is the same with no main-conversation context: a fresh thread with the session's workspace, settings and harness.

Either can be merged back into the main conversation:

* `:merge summary` (the default): `small_model` drafts a short note of what was found, and the user edits it before it lands.
* `:merge all`: every side turn grafted in, marked as from a side thread.
* `:merge pick`: the user chooses the turns.

What lands is a clearly marked note with a pointer to the side session, never a fabricated main-thread turn. Side threads are sessions listed under their parent (like subagents) and can be resumed; the harness treats their actions like any other, and an approval names the thread it comes from. On a local server with one slot, a side thread and a running main turn take turns. Builds on forks, `maic sessions graft` and `inject`. opencode has no equivalent (no `/btw` in its source as of 2fa3363c92); the name is Micaiah's.

### 4. Background agents and a switcher

Today a MAIC process runs one conversation in the foreground: Ctrl-Z suspends the whole process, a `task` subagent runs inside its parent's turn, and two agents mean two terminals. The plan: several agents (sessions) running at once in one MAIC, each with its own model, agent definition and workspace, and a switcher menu listing them with their state (working, idle, waiting for an approval, finished), model, and the working directory you land in by switching to each, so changing agents never surprises you with a different directory. Approvals from a background agent queue visibly and name the agent; `:btw` side threads appear in the same list. In maic.nvim each agent is a buffer. Builds on side conversations and the nvim interface's protocol; local only first, through maic-server later.
* **Sessions inside one MAIC** (Micaiah's idea): `:new` starts another session in the same interactive MAIC, `:switch` moves between them, `:fork` forks the live session into a second one (both stay open, the fork by pointer), `:bg` sends the live session to the background (it keeps working; the switcher shows its progress), `:park` ends a session for now (it stops, stays in the list and resumes where it was), and `:stop` ends it outright (a running turn is interrupted first, asking when one is in flight; it leaves the list of live and parked sessions and stays an ordinary transcript, resumable like any other with `maic -r`). Leaving a session through `:new`, `:switch` or `:fork` names what happens to the one being left with the same verbs (`--bg`, `--park`, `--stop`); without one, a working session goes to the background and an idle one is parked, and a global setting can make it ask instead. The switcher shows each one's workspace before you switch. **Built** (engine step 12, 2026-10-02): in the TUI and maic.nvim (`:MaicNew`, `:MaicSwitch`, ... each session a buffer), `session_leave` the global setting; background sessions live in the process that holds them until the daemon.
* **`task` subagents that do not block their parent**: today the parent's turn waits for the child's answer (it uses no CPU while waiting, but it cannot do anything else). `task` gains `background = true`: it returns a handle at once, the parent keeps working, and the child's answer arrives as a message at the parent's next step (the same mailbox mid-turn messages use), or through `task_result HANDLE`. Several children can run at once. Each child can run in its own process (forked, with the parent's harness and limits) so a crash or a runaway stays contained. On a local llama.cpp server with one slot, children and parent still take turns at the model; cloud providers run them truly in parallel. **Built** (engine step 14, 2026-10-02): `background: true`, `task_result`, each task a session of its own in the switcher (TUI and maic.nvim) that can be switched to, parked and stopped, its report a labelled note, its approvals raised on its parent's stream too, `max_tasks` (4) at once, the agent's `steering` and `protocol_tier` applied ([tools.md](tools.md)). The children run as threads of the engine, not processes of their own: that part is still to come.
* **A local MAIC daemon owns the sessions**, so a background session keeps running when the interface that started it switches away or closes: `maic` (the TUI), maic.nvim, the web app and a paired phone are all clients of it (the same protocol as the nvim interface), the way opencode's `serve`/`attach` split works, but local-first. It keeps an index of live, background and parked sessions in MAIC's state. **Built** (engine step 13, 2026-10-02): `maic daemon start|stop|status|run|unit`, the TUI and maic.nvim attaching when it runs, quitting leaving a working session working, the index in `<state>/engine/index.json`, the protocol tiers per session ([daemon.md](daemon.md)). The LAN and relay roles below are step 16.
* **Remote control without leaving anything on a middle-man**: a paired device asks the workstation (through the relay when away) for that index, picks a session, and the rendezvous opens for that session only then. A parked session can be resumed remotely whether or not remote control was enabled when it ran. Nothing is uploaded or mirrored anywhere while no device is asking. (opencode's sharing instead uploads the session to its own service, opncd.ai.)
* **The daemon is the server, or reaches one**: on the LAN the local daemon serves paired devices itself (maic-server's role); away from home it holds the outbound link to the rendezvous relay, as maic-server does today. Either way the workstation is the only place sessions live: the relay pairs the two ends and forwards end-to-end encrypted frames, storing nothing. A later upgrade lets the two ends go direct after the rendezvous (peer to peer, with ICE-style NAT traversal, the relay acting only as the meeting point and as the fallback path when a direct route cannot be made).
* **Remote reads lazily**: a remote client gets the current session and its last few exchanges up front, older history in chunks as it scrolls back (loaded and dropped as needed), and expensive items (large tool outputs, file contents, images) only when tapped open. Reduced capability remotely is accepted; the current session and its displayable history are what must always be there.
* **Starting the daemon**: not automatic at first. Later, MAIC can start it, saying so when the setup is a client only, and the repository ships baseline systemd user unit files that MAIC hands over or installs on request (Windows gets its own equivalent). `maic daemon unit install` writes the unit (step 13); enabling it stays your command, and MAIC starting the daemon itself is still to come.
* **Leaving a session, every case defined** (Micaiah, 2026-10-02): a `leave` table with a value for each case and no case left implied. Switching away: `idle = "park"`, `working = "bg"`, `after = "park"` (what a backgrounded session becomes when its task ends). Quitting: `idle = "stop"`, `working = "bg"` (a quit mid-task is a switch to the void: it keeps working), `after = "park"`. `no_daemon` says what a working session does at quit when nothing can keep it running. `--bg`, `--park` and `--stop` override any case for one leave. The defaults fill every case, the docs list each, and an unknown case or value is an error. To build after step 14.
* **Daemon modes, chosen at first start** (Micaiah, 2026-10-02): `off`; `on-demand`, a user daemon started when a quit leaves work running, which stops itself once every task is done (MAIC says that this mode cannot serve remote work); `constant`, always running, either as a self-repairing user daemon (a user unit that restarts itself, with lingering so it outlives the login) or as a system-level daemon. `constant` means any supervisor, recommended in this order: systemd (native to Linux; MAIC ships the units), then a container for anyone who would rather MAIC leave their systemd alone (Docker Engine or Podman, with a quick-start `compose.yaml` in the repository; the user runs the container side), then other free and open-source supervisors (pm2 can be named, with the note that a Node process manager minding a compiled program is a little silly, though it may be the best tool for someone's setup and we will not knock it until we have tried it there). MAIC recommends only FOSS/FLOSS tools, never closed-source or source-available ones; it may say that a non-free tool exists (Docker Desktop: the Docker CLI needs no desktop app), and suggests a clean-room FOSS replacement when a GUI is wanted. The client's container stays unprivileged and keeps the command sandbox working without `privileged: true`; anything that truly needs privilege goes in a second container, which belongs to the rendezvous or trusted-node side, not the client's userland. A system-level daemon still runs sessions as the user, never as root. `unmanaged`: the daemon run plainly, as `maic daemon start` does today, with no supervisor; it serves remote work like `constant`, but a crash is not repaired, it does not start at boot, and it can end with the login session. On first start MAIC asks which mode to set up; the answer is a setting and can be changed later.
* **Escalated privileges, always announced** (Micaiah, 2026-10-02, for all of MAIC): before any step that needs `sudo` (or polkit), MAIC says so and why. If you decline, it prints the bare command for you to run yourself and asks you to say when it is done. If the final answer is still no, it says what that leaves limited or not working as intended, and carries on without it.
* **Background task follow-ups** (Micaiah, 2026-10-02), to build next:
  * A task's report wakes an idle parent: it starts a turn, and the parent returns to idle through the usual lifecycle when nothing else is scheduled and no input comes.
  * `max_tasks` (4) is a global-only default you can raise; a project can only lower it, unless the global `project_limit_exceptions` list names that project with its own limit.
  * Paid or limited-free models (Claude Code presets and any other metered model) reached for automatically are never refused outright: MAIC asks first. Presets can name models as recommended when available and allowed. Loosening a global restriction goes through a tool that edits the global settings at your request.
  * A task's tokens count against the parent's budget as they are spent, through whatever keeps both local limits (the card) and remote limits (vendor quotas and bills) from being exceeded. Limits differ per model even under one vendor, so usage is tracked per model in levels that show you what your use implies.
  * Tasks run as threads today. Process containment comes later, with an explicit notion of a parent: a configurable limit of `n` parents; only the user starts a parent (a CLI command or a TUI command), and an agent may recommend one but never start it. A child that cannot find its parent gets a grace period of 0 ms to 3 h (configurable) when its transcript lets the work be picked up again, then ends itself, telling the user to start a new parent first. If the parent or child has a relay or trusted node connected, the child sends it a panic signal so the user can handle it remotely; if the parent was the remote server itself, the fix is in person, and the transcripts rebuild the work without loss.
* **Read-only transcript viewing** (Micaiah, 2026-10-02): open any transcript in a read-only mode with no agentic interaction at all. A visible file lock settles whether something is writing it; otherwise MAIC asks whether a process may write to it while it is read, and if so it leaves read-only mode only after several warning gates.
* **True parallelism is required**: background `task` children and background sessions run concurrently against API and CLI-agent providers; a local single-slot server serialises only what runs on it. Micaiah's priority: backgrounding is essential, not optional.
### 5. Layout files

The screen's layout comes from a file, so it can be rearranged without code: a layout file (Lua, like settings) names MAIC's panes (conversation, input, status strips, side threads, the agent switcher, approvals) and arranges them in splits with sizes, growth and visibility rules. Resolution follows the settings flow, with one difference: a baked-in default layout, then the closest file to the working directory wins, but layouts do not merge across layers. Exactly one layout file is used, and a nearer file builds on another only by importing it explicitly (`import = "default"`, then override the parts it names). The same file drives MAIC's own interface and, where it maps, the nvim interface's windows.

**Baked-in defaults as tracked files.** The defaults move out of the C++ into files in the repository (`defaults/settings.lua`, `defaults/layout.lua`, installed with MAIC), loaded as the bottom layer. `maic settings adopt FILE` takes a settings or layout file and writes only the values that differ into the tracked defaults file (showing the diff, asking first, keeping comments and order); everything the file does not define stays as it was. Run from a MAIC checkout it changes the repository's defaults, ready to commit. Depends on nothing; the panes for side threads and the switcher arrive with those items.
* **Which layout wins**: a project's layout beats the global one (trust applies: an untrusted project's layout is not read), and switching between the global chain and the project chain is one command (`:layout global|project|NAME`, for the session) or a setting.
* **Where `adopt` writes**: a global-only setting chooses the tracked defaults in the MAIC checkout, the user's copy in `~/.config/maic/defaults/`, or both; Micaiah's own setting writes the repository's defaults and keeps her `~/.config/maic` copy matching.
* **Preview before saving**: an in-tool layout view edits a working copy; each save previews it live in MAIC (and in nvim when connected), and only an explicit "apply" writes the real file. The layout model is chosen so it translates directly into nvim windows and splits.
* **Seeing the translation**: tooling and a doc that show exactly how one layout file renders in MAIC's own interface, in `maic --bare`, and in nvim, side by side: `maic layout show [FILE] [--views maic,bare,nvim]` renders one view by default and 1 + n views on request, so a change can be tuned while seeing every target at once. The doc walks through each pane's mapping (a split in MAIC becomes a window split in nvim, a status strip becomes a statusline or winbar, a floating approval becomes a float) and what cannot translate.

### 6. Accounts on maic-server

Micaiah's decision (2026-09-30): accounts belong to MAIC's own server, never to llama.cpp (which has API keys only, no identities). Design document first, then build; security-sensitive, so the design is reviewed before code.

* `maic join SERVER`: tells a client which maic-server to use (the `remote` setting plus a login); `maic open` and the apps then work against it.
* Login: username and password, or OAuth (sign in with a provider instead of a password; the provider configured per server; tokens never stored in plain text).
* Two-factor authentication on login (TOTP first, passkeys when the client can), per account, with a server setting that enforces it for everyone or leaves it optional.
* Email verification on signup: a code to the address, activation on confirmation. The mail step is the one outbound request MAIC's server makes, on the user's explicit action, configurable to a local relay.
* Best practice throughout: **argon2id** for password hashing (a hard requirement), short-lived session tokens with refresh and revocation, rate limits on login and codes, no secrets in URLs, a recovery path that does not weaken 2FA, the audit log naming the user.
* Per-user session ownership, an admin list, the per-device tokens folded into per-user ones.
* **Logins go stale, per device** (Micaiah, 2026-10-02): every device keeps its own login timer (about a week, configurable). Remote control is refused once a login is stale, until you log in again, in every daemon mode (`off` through `constant`), so a long-running daemon never keeps an old login alive. Logging in refreshes only the timer of the device that logged in.
* **A relay or trusted node checks both ends, pessimistic toward the workstation** (Micaiah, 2026-10-02): a node only forwards, so it checks the logins of both endpoints, the remote device and the workstation serving it. A fresh remote never vouches for an expired workstation: the workstation's expiry asks for a login on the device you are using, the prompt naming the workstation it re-validates, and that login refreshes only that workstation's timer; with several stale workstations, each needs its own login. A stale remote is asked to log in again, which refreshes the remote's timer and never the workstation's.

The relay (done) already carries the phone away from the LAN; accounts ride inside its tunnel unchanged.

### 7. One remote interface: MAIC plus llama.cpp

The web app and the phone apps present one clean interface that combines the MAIC server (sessions, approvals, the harness, services) and the llama.cpp server (models, loading and switching, sampling and XTC, a plain chat with the loaded model), so remote access gives both. llama.cpp stays behind MAIC's server, never exposed on its own; MAIC's server proxies what the app needs. A native client (Android first) follows the web app: notifications for pending approvals, pairing in the app, background reattach. Depends on 4 (accounts).

### 8. MAIC packages, laid out like nvim's

A package is a directory holding MAIC's runtime folders: `plugin/` (Lua run at start in MAIC's settings Lua state, with the user's trust, as nvim runs `plugin/`), `tools/` (Lua and script tools), `themes/`, `agents/` (opencode's agent file format, its `mode:` read as `role`) and `prompts/` (text for `--system @`). MAIC's runtime path, in order: `~/.config/maic`, the project's `.maic/`, MAIC's own `<data>/maic/site/pack/*/start/*` (and `opt/*` with `:packadd`), then nvim-managed plugins that carry a `maic/` folder. nvim never loads a `maic/` folder (it is not a runtime folder nvim knows), so one repository can ship an nvim side and a MAIC side and one package manager installs both; MAIC loads its part itself. Package management stays nvim's: lazy.nvim fetches, updates and pins (its `lazy-lock.json`), and MAIC only reads the result. Finding them without nvim running: lazy's root (`stdpath("data")/lazy`, the plugin list from the lock file) and nvim's `site/pack/*/{start,opt}`; inside an nvim host (maic.nvim), MAIC asks the host for its runtime paths, so lazy-loaded plugins are found exactly as nvim sees them. Tools a package adds are model-callable and so judged by the harness like any other; package startup code runs with the user's trust, as in nvim. `maic packages` lists what was found and from where. Depends on nothing; uses maic.nvim's host connection when present.

### 11. Security policies

Named, definable security policies (Micaiah, 2026-10-02): a policy is a set of settings that harmonize, with an official standard to follow and MAIC's base recommendation for each protocol tier (`open`, `guarded`, `airtight`) and for each role (workstation, relay, trusted node; a relay or node will want a much stricter one). The direction is always tight first, loosened on request. Settings already decided stay as they are until a security audit of the defaults, which marks items `flagged` without calling them critical safety issues unless they are.
