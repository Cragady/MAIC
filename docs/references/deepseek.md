## API facts for MAIC

### Endpoints and models

* Two wire formats on one host. OpenAI format: base `https://api.deepseek.com`, path `/chat/completions` (also `/completions` for FIM, `/models`, `/user/balance`, `/files`, and a Responses API under the same base). Anthropic format: base `https://api.deepseek.com/anthropic`, paths `/v1/messages`, `/v1/files`.
* The documentation shows the root `https://api.deepseek.com` with `/chat/completions`. A WorkBuddy configuration (community) uses `https://api.deepseek.com/v1/chat/completions`, which suggests a `/v1` path also works, while Oh My Pi's guide says not to append `/v1` to the base. Use the root form from the docs.
* Beta features (strict tool schemas, prefix completion, FIM) need the base `https://api.deepseek.com/beta` instead. The docs do not say whether stable features keep working on the beta base; treat it as a per-request choice, not a global one.
* Auth: `Authorization: Bearer KEY` on the OpenAI format; `x-api-key` on the Anthropic format (the Claude Code page uses a bearer token variable; the harness sends `x-api-key`). The Anthropic `anthropic-version` header is ignored; `anthropic-beta` is ignored for messages and required (`files-api-2025-04-14`) for the Files API.
* Current models: `deepseek-flash` (DeepSeek V4.1 Flash, text and image input) and `deepseek-v4-pro` (V4 Pro, text only). Context 1M tokens (the `/models` example reports 1,048,576), max output 384K (393,216). Both do thinking and non-thinking, JSON output, tool calls, prefix completion; FIM is non-thinking only.
* Legacy names `deepseek-v4-flash` and `deepseek-v4-flash-vision-exp` still work but are routed to V4.1 Flash and billed at Flash prices. `deepseek-chat` and `deepseek-reasoner` were scheduled to end on 2026-07-24 (they had pointed at V4 Flash non-thinking and thinking). Do not use legacy names.
* Model lifecycle conflict: the 2026-09-10 news post says that from 2026-09-14 04:00 UTC all `deepseek-v4-pro` requests are routed to V4.1 Flash at Flash rates until a V4.1 Pro ships. The change log entry of the same day says V4 Pro service continues after 2026-09-14 with billing unchanged, and the pricing page (read today) still lists V4 Pro with its own prices. Treat the pricing page as current, but log the `model` and `system_fingerprint` fields of every response so a silent re-route is visible.
* `GET /models` is machine-readable and worth using at start-up: per model it gives `context_window`, `max_output_tokens`, `input_modalities`, `effort.supported_levels` and `effort.default_level`, and `api_capabilities.anthropic_messages.system_prompt_update` (`in-history` or `leading-only`). In the documented example Flash is `in-history` and Pro is `leading-only`. `GET /user/balance` returns availability and CNY/USD balances (granted, topped up, total); useful for a budget display and for explaining a 402.

### Request fields (OpenAI format)

* Required: `model`, `messages`. Roles: `system`, `user`, `assistant`, `tool`. A `system` message may appear mid-conversation on this format; how it is treated depends on the model's `system_prompt_update` capability (below).
* Assistant messages accept `content` (string or null), `tool_calls`, `reasoning_content` (string or null), and the beta `prefix` flag. Tool messages need `tool_call_id`. Content may be an array of parts: `text`, `image_url` (`url` is an http(s) URL up to 8192 characters or a data URL; optional `detail` of `low`, `high`, `original`, `auto`), and `file` (`file_id` from the Files API, or `file_data` plus optional `filename`; mutually exclusive).
* `thinking`: object, `{"type": "enabled"|"disabled"}`, default enabled. `reasoning_effort`: top-level string, one of `none`, `low`, `high`, `max`; `none` also turns thinking off. Compatibility aliases accepted and mapped: `minimal` to `low`; `medium` and `xhigh` to `high`; `ultra` to `max`. Default effort is `high`. With the official OpenAI SDK, `thinking` must be passed through the raw-body escape hatch (`extra_body`); MAIC writes the JSON itself so this does not apply.
* `max_tokens`: 1 to 393,216. If omitted the default depends on mode: 8K without thinking, 64K with thinking, 128K with thinking at effort `max`. A long agent turn with reasoning can hit these defaults, so set it explicitly.
* `temperature` 0 to 2 (default 1) and `top_p` have no effect in thinking mode, except that `top_p` below 0.95 is raised to 0.95. Without thinking, `top_p` is fixed at 1.0 and ignored. `frequency_penalty` and `presence_penalty` are deprecated and ignored. None of these error.
* `stop`: up to 16 strings. `stream`, `stream_options.include_usage`. `stream_options` without `stream: true` is a 400. `logprobs` and `top_logprobs` (0 to 20); the response can carry logprobs for reasoning tokens too. `response_format`: `text` or `json_object`. `tools`, `tool_choice`. `user_id` (see isolation below).
* Tool definitions: `type: "function"`, `function.name` (letters, digits, underscore, dash, at most 128 characters, unique), optional `description`, `parameters` (JSON Schema; omitted means no parameters), optional `strict`.

### Thinking mode and reasoning replay

* Thinking is on by default. A harness that wants a non-thinking call (titles, summaries, quick classification) must send `thinking.type = disabled` or `reasoning_effort = none` explicitly.
* The chain of thought comes back as `message.reasoning_content` (non-streaming) or `delta.reasoning_content` (streaming), as a sibling of `content`, and streamed before the answer.
* Replay rule: when the request carries `tools`, the `reasoning_content` of all earlier assistant turns must be sent back, including turns that made no tool call. If it is missing the API answers 400 (the error text reported by a third-party client is "The reasoning_content in the thinking mode must be passed back to the API"). When the request has no `tools`, replayed `reasoning_content` is ignored and not added to the context.
* The simplest correct behaviour for MAIC: store `reasoning_content` verbatim next to every assistant message in the session file, and send it back on every assistant message while tools are attached. Sessions resumed from disk must replay it too, or the first request after `-r` will fail.
* Unsettled by the documentation: what to send for an assistant message that has no reasoning (a turn produced with thinking off, an old session, a turn from another provider) when thinking is on and tools are attached. opencode adds an empty `reasoning_content` to every assistant message for DeepSeek models; Pi's DeepSeek profile carries a flag meaning "replayed assistant messages need the field even if empty" (community). Sending an empty string is harmless where it is ignored and avoids the 400. The harness (Anthropic format) only replays reasoning that exists. Test with a real call before deciding.
* Another community profile also lists "assistant message with tool calls must have non-null `content`". The reference allows null, so this is unproven; sending an empty string instead of null costs nothing.
* Thinking with tool calls is supported (V3.2 onwards). A single user question can produce several reasoning-plus-tool rounds; each round's reasoning belongs in the history.
* `tool_choice` of `required` or a named function is rejected with 400 in thinking mode. `none` and `auto` are fine. To force a tool, turn thinking off for that call. (Oh My Pi's guide reports the same as "DeepSeek rejects tool_choice"; the reference page is more precise.) The harness does not map `tool_choice` at all.

### Tools

* Flow is the usual one: the model returns `tool_calls` (each with `id`, `type: function`, `function.name`, `function.arguments`), the harness runs them, and answers with one `tool` message per call carrying that `tool_call_id`. Echo the whole assistant message back, including `reasoning_content` and `tool_calls`.
* `function.arguments` is a JSON string that the model may get wrong or pad with parameters the schema does not define. Validate before executing. No-argument tools can arrive as `{}`.
* In a stream, the first chunk of each tool call carries `index`, `id`, `type` and `function.name`; later chunks for the same `index` carry only `function.arguments` fragments. Assemble by index. If the stream ends with `finish_reason: length`, the last call is probably cut off: drop it instead of running it (the harness's assembler does this).
* Parallel tool calls are possible in one assistant message; the docs describe no switch to turn them off on the OpenAI format (the Anthropic format accepts `disable_parallel_tool_use` but ignores it).
* Strict mode (beta, base `/beta`): every function in the request must set `strict: true`; every object schema needs `additionalProperties: false` and all its properties listed in `required`. Supported types: object, string, number, integer, boolean, array, enum, `anyOf`, `$ref`/`$def`. Strings take `pattern` and a few `format` values (email, hostname, ipv4, ipv6, uuid) but not `minLength`/`maxLength`. Numbers take min/max/exclusive bounds, `multipleOf`, `const`, `default`. Arrays need `items` and do not take `minItems`/`maxItems`. The server validates the schema and returns an error for anything unsupported. Works in both thinking and non-thinking modes. MAIC's tool schemas that use length or item-count limits cannot be sent strict as they are.
* Inserting tool calls that the model did not make (for example a synthetic read the harness performed) is supported on the Anthropic and Responses formats but not on Chat Completions. The harness additionally sends beta blocks for adding and removing tools mid-conversation under a dated beta header (`mid-conversation-tool-changes-2026-07-01`) and a deferred-loading marker; those two details come only from the harness README (harness), not from DeepSeek's reference.

### Streaming

* Server-sent events, `data: {...}` lines, ending with `data: [DONE]`. Chunk object is `chat.completion.chunk`; every chunk of a response has the same `id` and `created`. The first chunk carries `role: assistant` with empty content. The reasoning phase streams `reasoning_content` deltas first, then `content`, so a parser must not assume both arrive together, and a delta can have `content: null`.
* With `stream_options.include_usage` the final chunk (the one with a non-null `finish_reason` and exactly one choice with no new content) carries `usage`, and earlier chunks carry `usage: null`. There is no separate usage-only chunk before `[DONE]`, unlike the original OpenAI behaviour. Read usage from the last chunk, not from a trailing one.
* Keep-alive: while a request waits for the server to start inference, streaming responses emit comment lines (`: keep-alive`) and non-streaming responses emit empty lines before the JSON body. The SSE parser must skip comments, and a non-streaming client must tolerate leading whitespace.
* The server closes the connection if inference has not started after 10 minutes. So a client read timeout should be generous before the first token (queueing under load), and shorter between tokens afterwards. The harness's default stream idle limit is 300 seconds per read. Keep-alive comments are bytes on the wire, so an idle timer that resets on any byte will not detect a stuck queue; decide whether comments count.
* `finish_reason` values: `stop`, `length`, `content_filter`, `tool_calls`, `insufficient_system_resource` (the inference system dropped the request; sounds retryable), `aborted` (generation was interrupted). The last two are not in the usual OpenAI set; handle them as errors rather than as a normal end of turn.
* A stream that ends with `stop` and no content, no reasoning and no tool call has been seen in practice. The harness treats that as a retryable failure; a stream with reasoning only counts as content.
* JSON output with streaming still needs a closing `finish_reason` check: `length` means the JSON is cut off.

### Usage, caching and cost

* `usage` has `prompt_tokens` (equal to cache hit plus cache miss), `completion_tokens`, `total_tokens`, `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, `prompt_tokens_details.cached_tokens` (same number as the hit field), and `completion_tokens_details.reasoning_tokens` (the reasoning part of the completion). Reasoning tokens are billed as output.
* Context caching is automatic, on by default, with nothing to enable and no `cache_control` (the Anthropic endpoint ignores it). It works on stored prefix units, so a hit needs the new request to start with a whole stored unit; it is best effort, can take a few seconds to become available, and entries live for hours to days after last use. The docs give no minimum prefix length.
* Prices per million tokens, 2026-10-02: Flash cache hit $0.003 off-peak / $0.006 peak, cache miss $0.15 / $0.30, output $0.60 / $1.20. V4 Pro cache hit $0.022 / $0.044, miss $0.66 / $1.32, output $1.98 / $3.96. Peak is 01:00 to 04:00 and 06:00 to 10:00 UTC, Monday to Friday, excluding Chinese public holidays; everything else is off-peak at half price. A cache hit is roughly fifty times cheaper than a miss, so prefix stability dominates agent cost. The price table in the awesome-agent contribution guide is an older snapshot and disagrees with the pricing page; ignore it.
* To keep the prefix intact: do not reorder or edit earlier messages, keep the tool list identical between turns (a changed tool schema breaks reuse from the first changed token), keep the system prompt stable. For models whose `system_prompt_update` is `in-history` (Flash at the time of reading), a later `system` message in the history is read as the complete new system prompt, so a changed prompt can be appended instead of rewriting message 0 and losing the cache. This is the documented `/models` capability for the Anthropic format; the harness uses it on its Anthropic route, and the Chat Completions reference confirms that mid-conversation system messages are accepted. Only rely on it where `/models` says `in-history`.
* Output is still random even with a cache hit; caching affects input cost only.
* Offline token estimates: roughly 0.3 token per English character; a tokenizer package is offered for download. Image cost is capped at 1024 tokens per image (small images are scaled up toward about 544 by 544; large ones are scaled down to about 1300 by 1300 total pixels). The usage numbers returned are the truth.

### Errors and retry

| HTTP | Meaning in the docs | Treat as |
| :-- | :--- | :--- |
| 400 | malformed body, also the missing-`reasoning_content` case, `stream_options` without `stream`, `tool_choice` required or named under thinking, invalid strict schema | fix the request, never retry blindly |
| 401 | wrong API key | stop and tell the user |
| 402 | insufficient balance | stop; `GET /user/balance` explains it; never retry |
| 422 | invalid parameter values | fix the request |
| 429 | rate limit (concurrency, see below) | retry with backoff |
| 500 | server error | retry after a short wait |
| 503 | server overloaded | retry after a short wait |

* The error body format is not documented on the error page. Expect an OpenAI-style object; log the raw body.
* The harness's default policy (harness): up to five retries for empty responses, rate limit, server error, timeout and transport failure, exponential backoff from 0.5 s to 10 s with 10 percent jitter, and a provider `Retry-After` value replaces the local delay when it fits. Authentication, quota, invalid request and context overflow are never retried. It also keeps an optional unbounded mode for unattended runs. It marks each retry in the session log before waiting, so a long silent wait is visible.
* Context overflow has no dedicated documented error code; the harness maps a stable code for it. MAIC should recognise the message text from a real overflow when it first sees one and record it.

### Limits and isolation

* Rate limiting is by concurrent connections, not requests or tokens per minute: 2,500 for Flash and 500 for V4 Pro, counted per account regardless of which key sends the request. A request occupies a slot from sending until the reply is complete, and exceeding the limit returns 429. Subagents and parallel tool-using sessions share this pool.
* `user_id` (a top-level field on the OpenAI format, `metadata.user_id` on the Anthropic format; characters `a-z A-Z 0-9 - _`, at most 512; no personal data) separates users for safety review, for the KV cache and for scheduling. Accounts with raised quotas also get a per-`user_id` concurrency limit (an empty id counts as one user). Consequence: setting different ids per session splits the cache between them. Pick one stable id per person, or leave it out.
* Vision (Flash only): JPEG, PNG, GIF, WebP detected from content; 48 MiB request body; 32 MiB per image inline or by URL (URL download must finish in 60 seconds); 64 MiB per image via the Files API; at most 600 images per request. Files API: multipart upload to `/files` with `purpose=user_data`, optional expiry between one hour and thirty days, 64 MiB per file, upload must finish in 10 minutes. The harness uploads images once and references file ids, falling back to inline base64 for a single request if the upload fails, and never mixes the two within a request.

### Prefix completion, FIM and JSON output

* Chat prefix completion (beta, `/beta`): end the `messages` list with an assistant message that has `prefix: true`; the model continues from that text. Pair it with `stop` to cut the continuation. For thinking mode, that last message may carry a `reasoning_content` to continue the chain of thought. Useful for forcing an output shape such as an opening code fence.
* FIM (beta, `/beta`, `POST /completions`): `prompt`, optional `suffix`, `max_tokens` capped at 4K, `stop`, `stream`, `echo` (not together with `suffix` or `logprobs`); non-thinking only; response text is in `choices[0].text`. Relevant if MAIC adds editor-style completion.
* JSON output: `response_format: {"type": "json_object"}`. The prompt itself must also ask for JSON and show the shape; otherwise the model can stream whitespace until it hits `max_tokens`, which looks like a hung request. The API may occasionally return empty content in this mode (known issue, mitigate by retrying with a changed prompt). Set `max_tokens` high enough and check for `length`. The docs do not describe how it interacts with thinking or with tools.

### Anthropic-format endpoint: differences that matter

* Base `https://api.deepseek.com/anthropic`. Model names: any name starting `claude-opus` maps to `deepseek-v4-pro`; `claude-haiku` and `claude-sonnet` prefixes map to `deepseek-flash`; any unknown name falls back to `deepseek-flash`, silently. Send real DeepSeek names. (An opus-prefixed name bills at V4 Pro rates.)
* Supported with caveats: `max_tokens`, `stream`, `system`, `stop_sequences`, `temperature` (range 0 to 2, wider than Anthropic's own), `thinking` (`budget_tokens` is ignored, so a token budget does not control effort), `top_p` (only in thinking mode, minimum 0.95), `output_config` (only `effort`), `metadata` (only `user_id`), `tool_choice` with `none`, `auto`, `any`, `tool` (`disable_parallel_tool_use` ignored).
* Ignored: `top_k`, `container`, `mcp_servers`, `service_tier`, every `cache_control`, `citations`, and (important) `is_error` on `tool_result` blocks. A failed tool therefore looks successful to the model unless the failure text says so in the content itself.
* Content blocks supported: text, image (base64 of jpeg/png/gif/webp, URL, or Files API file), `tool_use`, `tool_result`, `thinking`, `server_tool_use`, `web_search_tool_result`. Not supported: `document`, `search_result`, `redacted_thinking`, MCP tool use and result, code execution result, container upload.
* Thinking switch and effort on this format: the thinking guide shows `reasoning` with an `effort` field (none, low, high, max), while the compatibility table says `output_config` supports only `effort`, and the harness (harness) actually sends `output_config.effort` for low, high and max and `thinking.type: disabled` for off. Three sources, two shapes; the harness shape is the one proven by a shipping client. Verify against the live API.
* Reasoning replay is built in: thinking blocks go back as `thinking` content blocks with their signatures. The harness stores the signature beside the block, restores it verbatim (including an empty signature), and drops signatures with a warning if its replay metadata is unusable. A Copilot CLI guide (community) says its OpenAI-type integration hits the missing-reasoning 400 while the Anthropic type does not, which fits.
* Tool-call history with unrepresentable arguments: on this format `tool_use.input` must be an object, so the harness sends `{}` for historical calls whose recorded arguments were malformed or not an object (the log keeps the original). On the OpenAI format `arguments` is a string and can be echoed unchanged.
* Mid-conversation tool insertion and system messages are supported here (see tools above). The Files API on this endpoint has Anthropic-shaped pagination and fields (`after_id`/`before_id`, `size_bytes`, RFC 3339 timestamps) and needs the beta header.
* The Claude Code integration page sets the main and sub-agent models to `deepseek-flash`, effort `max`, and an auto-compact window of 786,432 tokens (75 percent of the 1,048,576 window) as a suggested ratio.

### Surprising or easy to get wrong

1. Thinking is on by default, and `reasoning_effort` is a top-level field separate from `thinking.type`. The first summarising fetch put `reasoning_effort` inside `thinking`; the raw page and the SDK examples show it top-level.
2. A tool-using thinking session that drops any earlier `reasoning_content` gets a hard 400, not a quality drop.
3. `required` and named `tool_choice` fail under thinking.
4. `temperature` and `top_p` are silently inert in thinking mode, and `top_p` is clamped up.
5. Usage rides on the last content chunk; keep-alive comments and empty lines appear in both modes; `finish_reason` has two non-OpenAI values.
6. Unknown Anthropic model names silently become Flash; V4 Pro may be silently routed to Flash by DeepSeek (see lifecycle conflict).
7. The concurrency limit is account-wide and small for V4 Pro (500). 429 here means too many open requests, not too many per minute.
8. `max_tokens` defaults differ by thinking state and effort; reaching them yields `length` with possibly truncated tool arguments.
9. Beta features require the `/beta` base URL; strict mode needs every tool strict and every schema in a restricted subset.
10. `is_error` on tool results and `cache_control` are ignored on the Anthropic format.
11. A different `user_id` per session fragments the cache; the harness sends a stable anonymous id per installation.

## Harness lessons

Ideas only, from deepseek-harness (MIT), the agent lists, and a look at opencode. "MAIC" means the behaviour described in `docs/harness.md` and `docs/cleanroom.md` as of today; I did not read MAIC's provider code for this note.

### What deepseek-harness does that is worth weighing

* **Reconstructable requests.** Its rule is that anything that reaches the model must be recoverable from the session log. For DeepSeek that means the log keeps the exact reasoning text and the exact streamed order, so a resumed or forked session sends the same prefix and keeps cache hits. MAIC's transcripts already record each message as sent; the gap to check is that `reasoning_content` is stored verbatim for every assistant turn and replayed on resume.
* **Failed attempts are logged but are not history.** A failed or cancelled attempt is stored as a separate record with its partial stream, which never enters the next request. A cancelled stream's delivered text and reasoning are kept as an interrupted assistant message (tool calls that never ran are dropped), so "expand on your second point" still works after Esc. MAIC could mark interrupted turns in the same way.
* **Retry belongs to a policy, not to the loop.** Typed failure facts (HTTP status, `Retry-After`, request id) are carried with the error; a small set of transient codes is retried with backoff and jitter, and every retry is recorded before the wait. Empty completions count as transient failures. Nothing in a retry reaches the model.
* **Auxiliary calls change request settings.** Session-title requests force thinking off so the output budget goes to visible text; compaction calls carry a header that marks them as compaction. A MAIC summary or title call should disable thinking or use low effort instead of inheriting the main turn's settings.
* **Compaction is driven by the window, the output cap and a headroom.** The trigger is the smaller of 80 percent of the window and the window minus the output cap minus 64K, with the newest part of the conversation kept verbatim, one retry after a confirmed overflow, and a manual command. With a 1M window and a 256K output cap that comes to about 680K tokens. MAIC has a token budget (`budget_tokens`) and `:undo`; I did not see compaction on its built-list, so this is a candidate if long DeepSeek sessions are expected.
* **Cache-aware prompt updates.** A route capability says whether a changed system prompt may be appended later in the history instead of rewriting message 0; tool-schema changes are known to break reuse and are handled separately. MAIC should read `system_prompt_update` from `GET /models` instead of guessing from the model name (the harness itself says name-based inference is not sufficient).
* **Catalog of model facts is advisory data**, with the wire model id passed through unchanged so new DeepSeek models need no code change. A MAIC model table could be seeded from `/models` and overridable in settings.
* **Loop hygiene is advisory there.** A reminder after 3, 5 and 8 identical tool calls, tracked per agent and cleared by a new user message, never blocking. MAIC's rule is firmer (refuse at three, trip at five for writes, per its repeats entry), which suits its safety model; the harness's advisory text is a milder option for reads.
* **Tests.** It keeps unit tests, recorded-session replay without an API key, and a small key-gated end-to-end set that skips itself when no key is present (one case checks a tool round trip with reasoning replay at the highest effort; another compares cache reuse with thinking off). It ships two independent adapters against one neutral stream vocabulary to catch leaks of one provider's quirks. MAIC already has two wire formats (`anthropic.cpp`, `openai.cpp`) and recorded SSE fixtures; DeepSeek can be exercised through both, and a recorded stream containing reasoning, interleaved tool-call fragments, a keep-alive comment and a final usage chunk would pin the behaviours above.
* **Privacy: do not copy this part.** By default the harness sends an anonymous installation id, an application identity and a session id as headers, a list of loaded plugin packages, and an incremental copy of the whole session log (working directory, prompts, user and assistant text, tool arguments and results) as extra top-level fields in each model request. This contradicts MAIC's no-telemetry and no-phone-home rules and Micaiah's privacy preferences. A MAIC DeepSeek provider should send only the standard fields. The harness also labels its own Files-API image handling with the endpoint and credential so uploads are not shared across credentials; that part is sound.
* **Credentials.** Redirects are refused so the key never leaves the configured origin; failures name the config reference to fix and never print part of the key; a base URL with embedded credentials, a query or a fragment is rejected. All three fit MAIC.
* **Misconfiguration fails loudly at load**, with explicit defaults resolved in one place rather than hidden fallbacks. Same temperament as MAIC's settings handling.

### What the agent lists add

* The setup guides converge on the same compatibility traps: replay `reasoning_content`, do not send forced `tool_choice` under thinking, list the 1M window and 384K output cap, support effort `max`, use the official host rather than third-party gateways whose replay behaviour varies (community). Oh My Pi's guide notes that its per-model compatibility block replaces the built-in one wholesale rather than merging, a settings-design trap worth avoiding.
* Reasonix (described as cache-first with Flash by default, Pro armed on request or for a whole session, and automatic repair of tool calls) and DeepSeek-TUI (Plan, Agent and YOLO modes; effort cycling off, high, max; sandboxed tools) are described only by the list entries; I did not read their sources. The ideas worth noting: escalate to Pro per turn instead of per session, cycle effort from a key, and repair malformed tool-call arguments before executing.
* The contribution checklist is a useful summary of what DeepSeek itself considers the baseline for a new integration: current model names, the 1M window, max effort, current pricing, and no workaround that merely disables thinking.

### How opencode compares (MIT, read only for this note)

* opencode recognises DeepSeek by model id and appends an empty reasoning part to any assistant message lacking one, then writes the reasoning text into the `reasoning_content` field on every assistant message, even when empty, with a comment saying DeepSeek may return empty reasoning that still has to be sent back. That is the always-send-the-field choice discussed above.
* For OpenAI-compatible providers it lists the usual effort levels and adds `max` only when the id contains `deepseek-v4`. It keeps old model ids (`deepseek-chat`, `deepseek-reasoner`, `deepseek-r1`, `deepseek-v3`) in separate branches, which is the kind of legacy table MAIC can skip by supporting only the two current names.
* Its DeepSeek integration page asks for opencode 1.18.30 or newer, which matches the general pattern that clients need current builds for reasoning replay to work.

### Suggested checks before the integration is called done

1. A tool round trip with thinking at `high` and at `max`, then a second user turn, then a resume from disk, then another turn: all must succeed, and `prompt_cache_hit_tokens` should rise on the later requests.
2. A non-thinking call with `tool_choice` forced, and the same call under thinking to confirm the 400 is reported clearly.
3. A cancelled stream followed by a new turn.
4. A stream with a keep-alive comment and a final usage chunk, plus a `length` finish with a half-written tool call.
5. A 402 and a 429 path (a fake server is enough), each shown to the user with a distinct message.
6. Logging of `model`, `system_fingerprint`, `usage` and the retry history per turn.
